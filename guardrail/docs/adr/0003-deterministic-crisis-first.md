# ADR-0003: 위기 탐지를 결정적으로 먼저

**Date**: 2026-10-30
**Status**: proposed
**Deciders**: danielcho02
**PRD**: GR-06 (v4: GR-02, GR-03, GR-10, GR-14)

## v6 수정 (2026-11-10, R13 council)

이 블록이 아래 v5 블록과 본문보다 우선한다. PRD v6 GR-04·GR-06·GR-09 기준.
- **`emotional_distress`는 allow다.** 공개 세트에서 decision은 범주의 함수이고 `emotional_distress`는 allow였다([R13 §1 M1](../research/R13-design-research.md#1-근거-정리-research-ops-형식), [R13-A §1.2](../research/R13-public-set-analysis.md#12-범주별-단서와-분리력)). v5의 임시값 block은 버린다. decision은 코드가 범주에서 도출한다(ADR-0012).
- 위기는 이제 **범주 하나**일 뿐이다. 위기 전용 탐지기, 위기 어휘 목록, 차단보다 먼저 도는 경로, 실패 시 위기 우선 순위는 모두 없다(PRD GR-06에서 어휘 목록 삭제). 응답 문구·연락처는 `/tutor`의 `escalate` 몫이다(v5와 같음).
- **규칙 단서는 측정했다**: "몇 주째" + "혼자 버티기 힘들어/아무것도 하기 싫어"가 guard 4/4, tutor 9/9에서 emotional이고 normal에는 0건이다. "걱정·헷갈려·막막"만 있으면 normal이다(10건). 하지만 이 단서로 직접 결정하지 않고, 프롬프트 힌트로도 넣지 않는다. kNN few-shot 예시(ADR-0013)로만 nano에 닿는다. 범주 오류 1건은 약 0.08점이라 규칙으로 얻을 것이 작다([R13-A Q4](../research/R13-public-set-analysis.md#q4-가드-점수-상하한과-민감도)).
- 실패 기본값의 우선순위 목록(v5: jailbreak_injection > emotional_distress > …)은 D8로 바뀐다: kNN 다수와 LR이 같으면 그 범주, 다르면 LR, 없으면 `normal`(ADR-0009 v6).
- 본문의 pass^3 위기 세트 검사는 ADR-0006 v6의 빌드당 3회 실행으로 대신한다.

## v5 수정 (2026-11-09)

가드 응답에는 문구가 없으므로 위기 템플릿·연락처·T1–T3 하위 분류·"막을 때 위기 템플릿으로 응답"은 가드 범위에서 빠진다(응답 문구는 `/tutor`의 `escalate`가 맡는다). 남는 결정은 다음뿐이다.
- 골격 뷰 위 결정적 위기 어휘 매칭은 유지하고, 결과는 `emotional_distress` 후보 **힌트**로 입력 판정에 넘긴다(ADR-0002 v5). 입력 판정이 실패하면 이 힌트로 범주를 정한다(ADR-0009 기본값, 신호가 여럿이면 우선순위 jailbreak_injection > emotional_distress > pii_disclosure > low_signal_input).
- `emotional_distress`의 decision(allow/block)은 공개 세트로 정한다. 그 전 임시값은 block이다(PRD §3).
- 위기 어휘는 팀이 직접 쓴다. v4에는 어휘 파일이 없었다(R12 §8).
- 아래 v4 본문의 "위기 전용 분류 모델(P2)"은 대회 규칙상 불가다(학습 모델 파일 금지, OT p.25).

## Context

"위기 신호는 차단하지 않는다"는 원칙이 처음 초안에서는 LLM 정책 판정 안에만 있었다. council의 Critic이 이 구조에서 원칙이 조용히 깨지는 경로 세 가지를 찾았다.

1. 앞 단계의 규칙·분류기가 "치사량이 얼마야" 같은 질문을 공격으로 보고 먼저 막는다.
2. 판정 LLM이 장애로 멈추면 위기 여부를 알 수 없어서, 장애 시 "위기는 차단 안 함" 행을 적용할 수 없다.
3. 출력 PII 마스킹이 위기 템플릿의 02-735-8994를 `[전화]`로 바꾼다.

학생 서비스에서 위기 신호를 놓치면 그 실패 하나가 가장 무겁다. 발표 데모에서 터지면 안전 항목 전체에 대한 인상이 무너진다.

## Decision

LLM 없이 도는 **결정적 위기 탐지기**를 전처리 바로 다음, 어떤 차단보다 앞에 둔다.
- 골격 뷰(ADR-0001) 위에서 위기 어휘와 짧은 패턴으로 매칭한다.
- 위기로 잡혀도 차단 지점 네 곳(③ 규칙, ⑤ 입력 판정, ⑦ 카나리아, ⑧ 교환 판정)은 그대로 작동한다. 다만 막는 경우 거절 템플릿 대신 **위기 템플릿(연락처 포함)**으로 응답하고 대화를 끊지 않는다. 이것이 "위기는 차단하지 않는다"의 뜻이다. 위기 어휘를 덧붙여 차단을 건너뛰는 우회를 막기 위해서다(PR #1 santa 검토).
- 위기 어휘 매칭은 재현율을 우선한다. 원래 단어 경계를 넘는 매칭도 플래그로 인정하고, 오탐은 ⑤가 완화한다(ADR-0001 매칭 규칙).
- 위기 플래그는 입력 판정(ADR-0007의 ⑤)에 넘기고, **같은 호출**에서 위기 하위 분류(T1/T2/T3)와 오탐 완화를 한다. 별도 호출은 없다. 예를 들어 "숙제 때문에 죽겠다"에는 가벼운 안내를 하고 학습을 이어 간다. 입력 판정이 실패하면 T1 위기 응답으로 간다.
- `crisis_resources.yaml`의 번호는 PII 마스킹 허용 목록에 넣는다.
- 판정이 실패해 범주를 모를 때의 기본 응답에는 항상 위기 연락처를 붙인다.

## Alternatives Considered

### LLM 판정에만 위기 우선 규칙을 둠 (처음 초안)
- **Pros**: 문맥을 보고 판단해서 오탐이 적다.
- **Cons**: 위 실패 경로 1·2가 그대로 남는다.
- **Why not**: 가장 무거운 실패를 확률적 단계 하나에만 맡기게 된다.

### 위기 전용 분류 모델
- **Pros**: 완곡한 표현을 더 잘 잡는다.
- **Cons**: 학습 데이터와 시간이 들고, 장애 내성은 규칙과 같다.
- **Why not**: 재현율이 모자라는 부분은 LLM 판정이 2차로 보완한다. P2.

## Consequences

### Positive
- 판정 API가 꺼져도 위기 대응이 동작한다. 장애 주입 테스트로 증명할 수 있다.
- 위기 경로가 코드 몇 줄과 어휘 사전이라 리뷰와 회귀 테스트가 쉽다.

### Negative
- 재현율을 우선하므로 오탐이 생긴다. 정상 세트 오발동 ≤2%를 목표로 하고, LLM 2차 확인으로 응답 강도를 낮춘다.
- 어휘 사전에는 운영 부담이 따른다. 새 은어가 나오면 갱신해야 한다.

### Risks
- 사전에 없는 완곡 표현은 놓친다. 위기 세트를 직접·완곡·우회 표기로 나눠 재현율을 따로 보고하고, LLM 판정의 위기 범주를 2차 그물로 둔다.
- 테스트는 pass^3로 한다. 위기 세트를 3회 돌려 모두 통과해야 합격이다(eval-harness 핵심 경로 기준).
