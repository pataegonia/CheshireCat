# ADR-0004: 판정 모델은 생성과 다른 계열

**Date**: 2026-10-30
**Status**: proposed
**Deciders**: danielcho02
**PRD**: GR-04, GR-08, §6

## Context

가드는 입력 판정과 출력 교환 판정에 LLM을 쓴다. LLM 판정기는 자기 계열 모델이 쓴 글을 더 좋게 평가하는 편향이 있다(R7). 근거 판정에서 이 편향은 미탐으로 나타난다. 엘리스 ML API의 모델 목록, 단가, RPM, JSON 모드 지원은 아직 모른다. 판정 호출은 요청마다 1–2회 생기므로 비용 대부분이 판정기에서 나온다.

## Decision

- 판정 모델은 **생성 모델과 다른 계열의 저가 등급**에서 고른다.
- temperature는 0이다.
- 모델 이름은 코드에 넣지 않고 설정 파일에서 역할별(`input_judge`, `exchange_judge`)로 지정한다.
- 상위 모델로 올리는 것은 파싱 실패나 저확신일 때만 한다. 이 경로는 비율을 따로 기록한다.
- 호출 계층은 다음을 지킨다(cost-aware-llm-pipeline 패턴):
  - 실행 전 예산 상한을 확인한다.
  - 재시도는 일시적 오류(연결·429·5xx)만, 지수 백오프로 한다. 인증·요청 오류는 바로 실패시킨다.
  - 호출마다 토큰과 비용을 기록한다.

## Alternatives Considered

### 생성 모델이 스스로 판정
- **Pros**: 모델이 하나라 연동이 단순하다.
- **Cons**: 자기 선호 편향이 생긴다. 생성 모델이 공격에 넘어가면 판정도 같이 넘어간다.
- **Why not**: 계층을 겹친 의미가 사라진다.

### 상위 모델로 모든 판정
- **Pros**: 정확도가 높을 가능성이 있다.
- **Cons**: 비용과 지연이 몇 배로 늘고 RPM을 빨리 소진한다.
- **Why not**: GR-15 평가 예산과 §6 지연 목표를 맞출 수 없다. 저가 모델로 부족하다는 측정이 나오면 그때 바꾼다.

## Consequences

### Positive
- 생성 모델과 판정 모델이 동시에 같은 공격에 넘어갈 가능성이 줄어든다.
- 모델 교체는 설정 한 줄로 끝난다. 엘리스 목록이 나오면 바로 반영한다.

### Negative
- 계열이 둘이면 프롬프트와 출력 형식 차이를 둘 다 다뤄야 한다.
- 엘리스가 한 계열만 제공하면 이 결정은 지킬 수 없다.

### Risks
- 한 계열만 제공되는 경우: 같은 계열의 다른 크기 모델을 쓴다. 보고서에 편향 위험을 명시하고, 사람 라벨과의 일치도(GR-04)로 판정기 품질을 따로 보인다.
- 저가 모델이 한국어 근거 판정에서 약한 경우: 인용 실재 확인(ADR-0005)이 코드로 하한을 받친다.
