# ADR-0006: 평가 범위: 정적 세트 + 하네스, 확장 평가는 P2

**Date**: 2026-10-30
**Status**: proposed
**Deciders**: danielcho02
**PRD**: GR-15, GR-16, §7

## Context

조사 단계에서는 평가를 크게 설계했다.
- 3단 레드팀: 정적 / 자동(garak, promptfoo, 쿼리 예산 10·50·200) / 사람
- 상용 가드 기준선: OpenAI moderation, Bedrock
- 프레임워크 비교: NeMo Guardrails
- 한국어 테스트 매트릭스 약 7,300건, 항목당 3회 실행

하지만 혼자 4주 안에, 단가와 RPM도 모르는 API로 하기에는 호출 수가 수만 회에 이른다. 심사가 묻는 것은 적용 전후 비교, ablation, 트레이드오프 곡선, 지표 수치다.

## Decision

GR-15(P0)는 다음으로 한정한다.
- 정적 세트(개발·홀드아웃)
- 모의 튜터
- 주최측 평가셋 어댑터
- 단계 묶음 4개 단위 ablation
- 임계값 곡선
- 요청당 비용·지연

규칙도 정한다.
- 반복 3회 실행(pass^3, 한 번이라도 뚫리면 실패)은 홀드아웃과 위기 세트에만 쓴다.
- 실행 전에 예상 호출 수를 출력하고, 상한을 넘으면 멈춘다.
- 채점은 가능하면 코드로 한다. 카나리아, 인용 실재, 템플릿·연락처 존재가 여기에 해당한다. 공격 성공 여부만 LLM 판정기로 채점하고, 판정기와 사람 라벨의 일치도를 보고한다.

자동·사람 레드팀, 상용 기준선, 프레임워크 비교는 GR-16(P2)이다. 도구가 필요해지면 garak(Python)을 먼저 쓴다. promptfoo는 Node가 필요해서 두 번째다. 비교 대상은 NeMo Guardrails 0.24다. Guardrails AI는 Hub 종료가 예정돼 있어 제외한다.

## Alternatives Considered

### R8 원안: 3단 레드팀 + 7,300건 매트릭스 전체
- **Pros**: 적응형 공격에 대한 주장이 가장 강해진다.
- **Cons**: 시간과 API 예산을 넘는다. 가드 구현 시간을 잠식한다.
- **Why not**: council 네 목소리 모두 범위 과다로 봤다.

### 주최측 평가셋만 사용
- **Pros**: 심사와 같은 분포다.
- **Cons**: 형식과 공개 시점을 모르고, test는 직접 돌릴 수 없을 가능성이 크다. 한국어 우회와 위기 범주가 빠질 수 있다.
- **Why not**: 보고서 기여(자체 한국어 세트)와 위기 검증이 사라진다.

## Consequences

### Positive
- GP1부터 매주 같은 하네스로 수치가 나와서, 변경마다 개선을 보여 줄 수 있다.
- 예산 상한 덕분에 평가가 크레딧을 다 써 버리는 일을 막는다.

### Negative
- 보고서에서 "적응형 공격에도 강하다"는 주장은 할 수 없다. 정적 세트 기준임을 명시하고, 적응형 평가는 향후 과제로 둔다.
- 매트릭스를 줄이면 범주에 따라 59건에 못 미친다. 그런 범주는 "주장 불가"로 표기한다.

### Risks
- 개발 세트에 과적합할 수 있다. 경계 사례는 개발 세트에서만 뽑고, 홀드아웃은 1회만 돌린다. 원 요청 단위로 분리한다.
