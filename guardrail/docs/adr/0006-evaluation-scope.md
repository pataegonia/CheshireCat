# ADR-0006: 평가 범위: 정적 세트 + 하네스, 확장 평가는 P2

**Date**: 2026-10-30
**Status**: proposed
**Deciders**: danielcho02
**PRD**: GR-12, §7 (v4: GR-15, GR-16)

## v5 수정 (2026-11-09)

평가는 **공개 세트 + 대회 채점식 재현**으로 바꾼다(PRD GR-12). 모의 튜터, 외부 공격 세트, 공격 성공 판정기(`attack_judge.md`), 반복 3회 pass^3, 확장 평가(v4 GR-16)는 범위에서 빠진다. v4 자체 세트(LLM 초안)는 점수 보고에 쓰지 않고 개발 스모크로만 쓴다. v4의 단계 묶음 4개(입력·세션·검색·출력) ablation은 v5 단계 토글(GR-10: 결정적 신호·검색·사전 필터·구간 보정) ablation으로 바뀐다. 팀이 직접 쓴 한국어 우회·위기·인젝션 세트는 서버 밖 보조 평가로 쓴다(PRD §8, GG3).
- 데이터: `public/guard.jsonl`을 대화 단위·범주 층화로 개발/홀드아웃(약 30%) 분리. 홀드아웃은 잠그고 최대 3회만 본다. 1회는 한 세션에서 정해 둔 설정 묶음(베이스라인 + 후보) × 3회 반복을 한 번에 돌리는 것이다.
- 채점: block F1, non-normal 범주 정확도, 출력 판정 평균을 코드로 재현하고 `harness/score_local.py`와 값을 맞춘다.
- 첫 측정: 상수 응답(`allow`·`normal`, `grounded=true`·`unsupported=[]`·`safe=true`)의 점수(Skeptic). 출력 쪽 상수 점수가 이미 높으면 노력을 block F1에 둔다.
- 설정 비교는 McNemar(짝지은 검정), 점수는 부트스트랩 신뢰구간. 공개 세트가 수백 문항 규모라면 2–3%p 차이는 구별되지 않으므로 쫓지 않는다(R12 §3).
- 외부 공개 데이터셋은 운영진 확인 전에는 서버 밖 평가에도 쓰지 않는다.

## Context

조사 단계에서는 평가를 크게 설계했다.
- 3단 레드팀: 정적 / 자동(garak, promptfoo, 쿼리 예산 10·50·200) / 사람
- 상용 가드 기준선: OpenAI moderation, Bedrock
- 프레임워크 비교: NeMo Guardrails
- 한국어 테스트 매트릭스 약 7,300건, 항목당 3회 실행

하지만 혼자 4주 안에, 단가와 RPM도 모르는 API로 하기에는 호출 수가 수만 회에 이른다. 심사가 묻는 것은 적용 전후 비교, ablation, 트레이드오프 곡선, 지표 수치다.

## Decision

GR-15(P0)는 다음으로 한정한다.
- 정적 세트(개발·홀드아웃)
- 모의 튜터
- 주최측 평가셋 어댑터
- 단계 묶음 4개 단위 ablation
- 임계값 곡선
- 요청당 비용·지연

규칙도 정한다.
- 반복 3회 실행(pass^3, 한 번이라도 뚫리면 실패)은 홀드아웃과 위기 세트에만 쓴다.
- 실행 전에 예상 호출 수를 출력하고, 상한을 넘으면 멈춘다.
- 채점은 가능하면 코드로 한다. 카나리아, 인용 실재, 템플릿·연락처 존재가 여기에 해당한다. LLM 판정기(`prompts/attack_judge.md`)는 **공격 성공**과 **정상 항목의 자체 거절(`refused`)** 두 가지만 채점하고, 판정기와 사람 라벨의 일치도를 보고한다(2026-11-03 S0.7에서 넓힘, 아래).

자동·사람 레드팀, 상용 기준선, 프레임워크 비교는 GR-16(P2)이다. 도구가 필요해지면 garak(Python)을 먼저 쓴다. promptfoo는 Node가 필요해서 두 번째다. 비교 대상은 NeMo Guardrails 0.24다. Guardrails AI는 Hub 종료가 예정돼 있어 제외한다.

### 판정기 범위 확대 (2026-11-03, S0.7, master-plan §4.7)

과잉 거절은 가드 템플릿(거절·전환·부분·위기)만 코드로 세면 무방비 베이스라인에서 늘 0이 된다. 무방비 튜터도 생성 모델이 스스로 거절하는데, 그 거절이 빠지면 전후 비교가 공정하지 않다. 그래서 정상 항목(benign·benign_risky·greeting)도 판정기를 한 번 부르고 `refused`로 모델 자체 거절을 센다.
- 순서: 판정기 전에 trace로 먼저 가른다. `fallback_infra`이면 인프라 폴백, R3 폴백·"교재에서 찾지 못했어요."이면 근거 폴백, 가드 템플릿이면 과잉 거절이고, 이 경우 판정기를 부르지 않는다. 두 폴백은 과잉 거절에 넣지 않는다.
- 예산 영향: 정상 항목마다 판정기 1회. 스모크(정상 50건)에서 50회, GP2 정상 세트에서도 항목 수만큼 늘고, `--estimate` 추정 공식이 이것을 센다(attack·benign·benign_risky·greeting은 attack_judge 1).
- 판정기 오류(형식 재요청 뒤에도 파싱 실패, 타임아웃)는 그 항목을 error로 분모에서 빼고 건수를 따로 보고한다.

## Alternatives Considered

### R8 원안: 3단 레드팀 + 7,300건 매트릭스 전체
- **Pros**: 적응형 공격에 대한 주장이 가장 강해진다.
- **Cons**: 시간과 API 예산을 넘는다. 가드 구현 시간을 잠식한다.
- **Why not**: council 네 목소리 모두 범위 과다로 봤다.

### 주최측 평가셋만 사용
- **Pros**: 심사와 같은 분포다.
- **Cons**: 형식과 공개 시점을 모르고, test는 직접 돌릴 수 없을 가능성이 크다. 한국어 우회와 위기 범주가 빠질 수 있다.
- **Why not**: 보고서 기여(자체 한국어 세트)와 위기 검증이 사라진다.

## Consequences

### Positive
- GP1부터 매주 같은 하네스로 수치가 나와서, 변경마다 개선을 보여 줄 수 있다.
- 예산 상한 덕분에 평가가 크레딧을 다 써 버리는 일을 막는다.

### Negative
- 보고서에서 "적응형 공격에도 강하다"는 주장은 할 수 없다. 정적 세트 기준임을 명시하고, 적응형 평가는 향후 과제로 둔다.
- 매트릭스를 줄이면 범주에 따라 59건에 못 미친다. 그런 범주는 "주장 불가"로 표기한다.

### Risks
- 개발 세트에 과적합할 수 있다. 경계 사례는 개발 세트에서만 뽑고, 홀드아웃은 1회만 돌린다. 원 요청 단위로 분리한다.
