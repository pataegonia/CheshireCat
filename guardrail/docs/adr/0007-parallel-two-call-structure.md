# ADR-0007: 입력 판정과 생성 병렬, 요청당 판정 2회, 차단 권한 4곳

**Date**: 2026-10-30
**Status**: proposed
**Deciders**: danielcho02
**PRD**: §4, GR-04, GR-05, §6

## Context

PRD v2는 모든 단계를 한 줄로 이어 놓았다(입력 판정 → 생성 → 교환 판정). 이 구조에는 두 가지 문제가 있다.
- **지연이 더해진다.** 입력 판정 1.5s, 검색과 생성 2–4s, 교환 판정 1.5s를 차례로 거치므로 추정 5–7s가 걸린다.
- **오차단이 합쳐진다.** 여러 계층이 각자 차단할 수 있어서 과잉 거절이 누적된다. 7계층 스택이 정상 프롬프트 5개 중 4개를 거부했다는 측정이 있고, 계층 간 실패는 서로 양의 상관을 보였다(arXiv 2608.28327).

다른 시스템의 방식은 이렇다. OpenAI Agents SDK는 입력 가드레일을 기본적으로 에이전트와 병렬로 돌린다. Anthropic CC++는 입력과 출력을 하나로 묶은 교환 단위로 판정한다. 근거는 [R10](../research/R10-architecture-options.md)에 정리했다.

## Decision

- 코드 단계(정규화, 위기 어휘, 확실한 규칙, PII 마스킹)는 직렬로 먼저 끝낸다.
- 그다음 **입력 판정과 튜터의 검색·생성을 동시에 시작**하고, 합류 시점에 판정 결과를 적용한다.
  - 차단: 생성 결과를 버린다.
  - 전환·부분 응답: 지시를 붙여 다시 생성한다.
  - 허용: 생성 결과로 계속 진행한다.
  - 위기(T1–T3): 생성 결과를 버리고 위기 템플릿으로 응답한다.
  - 위기 오탐(가벼운 안내): 생성 결과를 유지하고 짧은 안내를 덧붙인다. 출력 검사는 그대로 거친다.
  - 입력 판정 실패·타임아웃: 생성 결과를 버리고 연락처를 붙인 안전 응답으로 대체한다. 위기 플래그가 있으면 T1 위기 응답이다(PRD GR-14).
- 출력 쪽은 코드 검사 다음 LLM 교환 판정을 1회 하고 수리한다.
- 멀티턴 재판정은 별도 호출로 하지 않는다. R이 임계값 이상이면 다음 입력 판정에 넣는 문맥을 4턴에서 8턴으로 넓힌다.
- 위기 어휘가 잡힌 입력은 위기 플래그와 함께 입력 판정에 넘겨 같은 호출에서 하위 분류를 한다. 차단 지점은 그대로 작동하고, 막을 때는 위기 템플릿으로 응답한다(ADR-0003).
- 판정 호출은 기본 2회다. 추가 호출은 R2 재생성 뒤 재판정(튜터가 콜백을 줄 때, ≤15%)과 형식 오류 재요청뿐이다.
- 차단 권한은 네 곳에만 둔다.
  - 결정적: 확실한 규칙, 카나리아
  - 확률적: 입력 판정의 고신뢰 차단, 교환 판정의 유해·정답 유출
- 과잉 거절은 파이프라인 전체로 측정해 보정한다.

## Alternatives Considered

### A. 직렬 (PRD v2)
- **Pros**: 가장 단순하다. 차단된 요청에는 생성 비용이 들지 않는다.
- **Cons**: 입력 판정 지연이 그대로 더해지고, 차단할 수 있는 계층이 많다.
- **Why not**: 같은 판정 품질이면 B가 1.5s(추정) 더 빠르다. 대신 엘리스 API가 동시 호출을 막는 경우에 쓸 대체 모드로 설정에 남긴다.

### C. 교환 판정만 (CC++ 방식)
- **Pros**: 호출이 1회라 가장 싸다. 지연은 B와 같다.
- **Cons**: 입력 의도 신호가 없다. 그래서 전환·부분 응답과 멀티턴 R을 판단할 근거가 약하고, 튜터 PRD FR-02(입력 가드)를 충족하지 못한다.
- **Why not**: B에서 입력 판정을 끄면 C가 된다. ablation으로 측정해 입력 판정의 순기여를 보고한다.

### D. B + 문장 단위 점진 표시
- **Pros**: 첫 문장이 가장 빨리 나온다.
- **Cons**: 정답 유출처럼 여러 문장에 걸친 위반을 잡기 어렵고, 수리 범위가 줄며, 호출이 늘고, 마지막 구간을 다시 검사해야 한다(Azure 공식 경고).
- **Why not**: P2 실험으로 둔다.

## Consequences

### Positive
- 입력 판정 지연이 생성 시간 뒤에 숨는다.
- 판정 호출이 요청당 기본 2회라 비용 예측이 쉽다. 예외 경로(R2, 재요청)는 비율로 따로 기록한다.
- 차단 권한이 줄어 오차단이 누적되는 경로가 짧아진다.

### Negative
- 차단된 요청에도 생성 비용이 든다. 공격 평가 세트에서는 이 낭비가 크므로 GR-15 예산에 반영한다.
- 전환·부분 응답이 나오면 해당 턴은 재생성 때문에 지연된다.
- 요청당 동시 호출이 2개가 된다.

### Risks
- 엘리스 API가 동시 호출을 제한하면 설정으로 직렬 모드로 전환한다. 이 경우 직렬과 병렬의 지연 비교 결과가 그대로 보고서 재료가 된다.
- 입력을 바꾸는 단계가 병렬 구간에 들어가면 경쟁 조건이 생긴다(NeMo 경고). 정규화와 PII 마스킹은 분기 전에 끝낸다.
- 병렬 구조로 줄어드는 지연은 공개된 실측이 없다. 우리 하네스로 직접 측정한다.
