# ADR-0010: 가드 쪽 KB 검색

**Date**: 2026-11-09
**Status**: proposed
**Deciders**: danielcho02 (council 2026-11-09)
**PRD**: GR-03, GR-07

## R14 수정 (2026-11-13, R14 council)

이 블록이 아래 v6 블록의 "쓰는 범위" 한 줄보다 우선한다. 나머지는 그대로다.
- **출력 nano에 주는 문맥**: 상위 3조각 대신 **1위 섹션 전체**(`section_text`, `output.context_max_chars`로 자름) + 상위 3조각 중 다른 섹션의 조각([R14 §6](../research/R14-prompt-uplift.md#6-council-2026-11-13-후보-선별) R14-D4). 조각으로 자르면 변조된 문장의 원문이 빠져 nano가 "자료에 없음"으로 볼 수 있다. 같은 데이터로 두 방식을 비교한 측정은 없고(R14-B2 §1-4), 규칙 ②가 이미 섹션 전체를 본다는 점에 맞춘 설계다. 공개 KB 섹션은 CSV를 합쳐 1,600–2,700자다. 정답 섹션이 1위가 아닌 3/67행은 다른 섹션 조각이 받친다. 개발 실행은 행마다 정답 섹션이 1위였는지 남긴다.

## v6 수정 (2026-11-10, R13 council)

이 블록이 본문보다 우선한다(본문이 v5다). PRD v6 GR-03 기준.
- **BM25 구현은 R13-A가 잰 변형을 옮긴다**: `guardrail/scripts/r13/common.py`의 BM25(문자 2-gram, k1=1.2, b=0.75)다. 이 BM25는 질의 2-gram의 빈도를 무시한다(질의의 서로 다른 2-gram에 대해서만 합산). 규칙의 `rule_min_margin`이 절대 점수에 걸리므로 이 성질까지 그대로 옮기고 `common.py`와 점수가 같은지 테스트한다(C2 S2.2). 토큰화는 `scoring.normalize`식(NFKC, 소문자, 공백·문장부호 제거 뒤 문자 2-gram)이다. 조각은 `common.kb_chunks`를 그대로 옮긴다. 섹션 텍스트(md + 붙은 CSV)를 `## `로 시작하는 줄 앞에서 자른다(`re.split(r"\n(?=## )")`). 코드 블록 안의 `## ` 줄에서도 자른다(PR-02-01에 3곳). 각 조각은 자기 `## ` 소제목 줄을 포함하고, 첫 `## ` 앞의 `# 제목` 머리말은 따로 한 조각이 된다. 조각마다 문서 제목을 덧붙이지 않는다. CSV는 섹션 끝에 붙어 마지막 조각에 들어간다. 코드 블록을 자르지 않는 변형은 다시 재야 하는 ablation이다. 본문의 "`mock_tutor.py` 구현을 옮김"은 버린다(그 변형은 측정하지 않았다). 아래 목표(1위 ≥64/67, 3위 ≥66/67 = 측정값 96%·99%, 규칙 기본 변형 V2의 U 18/35 · G 0/32 · T 6/119, [R13-A §6](../research/R13-public-set-analysis.md#6-규칙-②-오탐-재측정-santa-4라운드))는 이 변형의 값이다. 원래 `NUM_RX`의 18/35·오탐 0/32는 가드만 본 기록이다. 구현이 달라지면 다시 잰다. 이 NFKC는 BM25 토큰 안에서만 쓴다. 정규화본에는 여전히 NFKC를 쓰지 않는다(ADR-0001).
- **조각은 `##` 소제목 단위**다(위 `kb_chunks` 그대로). 같은 이름의 CSV는 그 섹션에 붙이고, 조각에 섹션 ID를 단다. 공개 세트 정답 섹션 1위율이 섹션 단위 93%에서 `##` 조각 96%로 올랐다([R13-A §5.2](../research/R13-public-set-analysis.md#52-char-2gram-bm25로-정답-섹션-찾기)).
- **질의 = 창 안의 학습자 발화 + 후보 답변, 한 덩어리**([R13 D7](../research/R13-design-research.md#3-결정-d1d10)). 아래 본문의 "답변 문장별 질의, 답변 전체 질의 금지"를 버린다. 이 질의로 1위 96%, 3위 99%를 쟀다(학습자 발화 전체만, 조각 단위면 90%·97%. [R13-A §5.2](../research/R13-public-set-analysis.md#52-char-2gram-bm25로-정답-섹션-찾기) 표의 '전체 user, `##` 청크' 행으로 같은 조각 단위끼리의 비교다). 답변만 질의는 97%·100%였지만 정답 섹션 배정에 답변을 썼으므로 낙관적이다([R13-A §5.2](../research/R13-public-set-analysis.md#52-char-2gram-bm25로-정답-섹션-찾기)). 측정한 질의는 모든 user 발화 + 답변(`all_user + "\n" + candidate_answer`)이다. 가드 공개 세트는 메시지가 5개 이하라 창(첫 학습자 발화 + 마지막 6개) 안의 학습자 발화와 같다. 튜터 공개 세트는 최대 11메시지(7개 초과 58행)라 창과 다르지만, 창 질의로 q6를 다시 돌려도(`q6_rule_fp.py --window`) U·G·T 수치와 F1이 같았다([R13-A §6](../research/R13-public-set-analysis.md#6-규칙-②-오탐-재측정-santa-4라운드)). Critic의 오염 우려(지어낸 내용이 비슷한 구절을 끌어옴)는 측정에서 드러나지 않았다. 근거 없음 35행 중 32행이 정답 섹션을 1위로 찾았다.
- **쓰는 범위**: 출력 nano 판정에는 상위 3조각, 숫자·리터럴 규칙에는 1위 조각의 섹션 전체(같은 `section_id`의 모든 조각 + 붙은 CSV)를 쓴다. 규칙의 비교 범위를 1–3위 합집합으로 넓히면 탐지가 18건에서 13건으로 줄었다([R13-A §5.1](../research/R13-public-set-analysis.md#51-35행-전체-참-사실-위치와-변조-유형)).
- **1·2위 점수 차 게이트**: 1위 섹션과 그와 **다른** 섹션 중 최고 점수의 BM25 점수 차가 기준보다 작으면 근거 섹션이 불확실하므로 숫자·리터럴 규칙을 끈다(ADR-0014). 기준은 설정(`rule_min_margin`, 기본 3.5(잠정), GR-11)이고 S3.1이 가드 근거 있음(G)만이 아니라 G∪튜터 참조 답변(T) 오탐으로 정한다. 공개 기준 m = 3.5면 U 16/35, G 0/32, T 3/119다([R13-A §6.2](../research/R13-public-set-analysis.md#6-규칙-②-오탐-재측정-santa-4라운드)).
- **Kiwi는 쓰지 않는다**([R13 D7](../research/R13-design-research.md#3-결정-d1d10)). 본문 Context의 "학습된 형태소 분석기는 쓸 수 없다"는 SPEC §7.1과 다르다. SPEC은 사전이 딸린 형태소 분석기를 허용한다. 다만 `kiwipiepy_model`의 언어모델 파일은 "미리 학습된 모델"과 경계가 모호하고([R13-B2 §2](../research/R13-B2-libraries.md#2-규정-판정-기준과-모호한-지점)), 문자 2-gram BM25가 이미 96%라 주최측 답이 와도 넣지 않는다.
- **임베딩 혼합 검색은 ablation**(P2). 3위 밖 실패는 영어 질의 1건(pub-763823ae)뿐이었다. 켜면 KB 임베딩은 기동 때 만들고(SPEC §7.1), 요청당 임베딩 호출이 1회 는다.
- 색인은 기동 때 만든다(SPEC §3). `/tutor`와 색인 공유는 PRD §9 제안이다.

## Context

`/guard` 요청에는 근거 자료가 없다. 후보 답변이 자료에 근거했는지 판정하려면 가드가 지식 베이스(`kb/<과목>/`, 섹션 하나가 마크다운 파일 하나, 표는 같은 이름의 CSV)를 직접 찾아야 한다. 학습된 형태소 분석기(kiwipiepy, Mecab)는 모델·사전 파일을 담고 있어 쓸 수 없다. 임베딩은 `text-embedding-3-small`만 쓸 수 있고 호출마다 API를 부른다(R12 §6-1).

Critic이 짚은 위험: 후보 답변을 통째로 질의에 넣으면, 지어낸 내용과 겉보기에 비슷한 구절이 검색돼 판정기가 근거 있다고 볼 수 있다. 고정 길이 청크는 CSV 표와 코드 블록을 자른다.

## Decision

- **청크 단위는 섹션**(파일 하나). 같은 이름의 CSV는 그 섹션에 붙인다. 섹션이 판정 프롬프트에 넣기에 너무 길면 마크다운 소제목 단위로 나누되 코드 블록·표는 자르지 않는다.
- **검색은 기존 문자 2-gram BM25**(`src/guardrail/eval/mock_tutor.py`의 구현을 서버 모듈로 옮김). 새 의존성 없음. 색인은 기동 때 만든다.
- **질의는 후보 답변의 문장별 + 입력 판정과 같은 창(첫 학습자 발화 + 최근 6턴)의 학습자 발화.** 학습자는 실습·예제 이름을 어느 턴에서든 말할 수 있고, 버튼 문구로 시작한 대화는 실제 질문이 다음 발화에 온다(OT §4). 문장마다 top-k를 구해 합치고(섹션별 최고 점수), 상위 섹션을 판정기에 넣는다. 답변 전체 한 덩어리 질의는 쓰지 않는다.
- k와 넣을 섹션 수는 `public/tutor.jsonl`의 정답 근거 섹션으로 recall@k를 재서 정한다.

## Alternatives Considered

### 임베딩 검색 / BM25 + 임베딩 혼합
- **Pros**: 바꿔 말한 표현에 강하다
- **Cons**: 요청마다 임베딩 호출이 늘어 호출 수·지연·키 회수 위험이 커진다(Skeptic). 효과가 측정되지 않았다
- **Why not**: 지금은 아니다. recall@k에서 BM25가 놓치는 사례가 확인되면 ablation으로 더한다. KB 임베딩은 기동 때 미리 만든다

### 과목 전체를 프롬프트에 넣기(검색 없음)
- **Pros**(Critic): 검색 오류가 사라진다. 과목 하나가 작으면 가능
- **Cons**: 과목을 고르는 단계가 필요하고, 입력 토큰이 커져 지연·한도에 불리하다
- **Why not**: KB 크기를 모른다. 11/10에 과목별 토큰 수를 재고, 과목당 약 2만 토큰 이하이면 비교 실험한다

### 후보 답변 전체를 한 번에 질의
- **Why not**: 지어낸 내용이 비슷한 구절을 끌어와 판정을 오염시킨다(Critic)

## Consequences

### Positive
- 외부 호출 없이 1ms 단위로 돈다. 규칙 위반 위험이 없다
- 섹션 ID가 그대로 남아 판정 근거를 추적할 수 있다

### Negative
- 어휘가 다른 바꿔 말하기에 약하다
- 문장별 질의는 답변이 길면 검색 횟수가 늘어난다(CPU 비용은 작음)

### Risks
- 가상 설정(다람쥐은행 등)은 일반 상식과 다르다 → 판정 프롬프트에 "근거는 KB만"을 명시한다(ADR-0011)
- recall이 낮으면 출력 판정 전체가 무너진다 → 11/10 첫 측정 항목으로 둔다
