# R10 · 가드레일 아키텍처 수정안: 다른 LLM 가드레일 비교와 제안

작성 2026-10-30 · `/ecc:deep-research` · 대상: PRD v2 §4 구조(직렬 8단계)

**결론**
- 직렬 구조를 **"코드 검사(직렬, ms) → LLM 입력 판정 ∥ 검색·생성 → 코드 검사 → LLM 교환 판정 1회"**로 바꾼다.
- 요청당 LLM 판정은 **기본 2회**다(R2 재판정 ≤15%와 형식 오류 재요청은 별도).
- 확률적으로 차단할 수 있는 계층은 **둘뿐**이다(입력 판정 고신뢰, 교환 판정의 유해·유출). 나머지는 점수, 수리, 표시로 처리한다.
- 입력 판정 지연은 생성 시간 뒤에 숨는다.
- 과잉 거절은 계층별로 보정하지 않고, 파이프라인 전체(end-to-end)로 보정한다.

## 2. 구조 설계에 쓰는 근거

1. **오차단은 합집합으로 쌓인다.**
   - "Layered LLM Defenses as an Ensemble"(arXiv 2608.28327, 초록 확인)에서 7계층 스택이 정상 프롬프트 5개 중 4개를 거부했다.
   - 같은 논문에서 계층 간 실패 상관은 측정한 15쌍 모두 양수였다. 즉 안전 이득은 곱으로 늘지 않는다.
   - 계산: 계층별 오차단 2%짜리 5개를 쌓으면 1−0.98⁵ ≈ 9.6%다.
2. **CivicShield**(2603.29062)는 중간 계층이 단독으로 차단하지 않고 누적 위험 점수에만 기여하게 설계했다(합성 FPR 약 7.8%는 추정치).
3. **병렬 가드의 실측 절감률은 공개된 자료가 없다.** 이론상 절감은 min(입력 판정 지연, 검색+생성 지연)이다. 생성이 판정보다 길면 판정 지연이 전부 숨는다.
4. **단일 호출로 여러 과제를 판정할 때의 정확도 손실을 직접 비교한 연구는 없다.**
   - 지시 수가 늘수록 성능이 떨어진다는 간접 증거만 있다(2509.21051).
   - 따라서 판정 항목을 3–4개로 묶는 것은 A/B로 확인한다.
5. **한국어로 바로 쓸 수 있는 저지연 근거성 검출기는 없다.**
   - HHEM 오픈판, Azure 근거성 검사는 영어만 지원한다. MiniCheck은 자체 호스팅이 필요하다.
   - API 전용이라면 **범용 LLM 1회 호출로 모든 문장을 함께 판정**하는 방식이 남는다(ADR-0005 유지).
6. **스트리밍 문장 버퍼**: SentGuard(2606.02041, 초록만)는 불안전의 90.5%를 2문장 안에 잡지만 스트리밍 FPR이 7.41%다. 정답 유출처럼 여러 문장에 걸치는 위반은 문장 단위로 잡기 어렵다.

## 3. 후보 구조 비교

G = 검색+생성 시간(미측정, 2–4s로 가정), J = LLM 판정 p95(1.5s 목표). 아래 지연은 모두 **추정**이다.

| 구조 | 흐름 | 지연(추정) | 판정 호출 | 확률적 차단 계층 | 장점 | 단점 |
|---|---|---|---|---|---|---|
| A. 현재 PRD v2(직렬) | 코드 → 입력 판정 → 생성 → 교환 판정 → 수리 | J + G + J ≈ 5–7s | 2–3 (재판정 포함) | 4–5 | 단순 | 지연 누적, 오차단 누적 |
| **B. 제안: 병렬 2호출** | 코드 → (입력 판정 ∥ 생성) → 코드 → 교환 판정 → 수리 | max(J, G) + J ≈ 3.5–5.5s | 2 | 2 | 지연 은닉, 생성 전 차단과 의도 판정 가능 | 차단 요청은 생성 비용 낭비, 전환·부분 응답이 필요하면 재생성 |
| C. 교환 판정만(CC++형) | 코드 → 생성 → 교환 판정 → 수리 | G + J ≈ 3.5–5.5s | 1 | 1 | 가장 싸다 | 입력 의도 신호가 없어 멀티턴 R과 의도 기반 전환이 약하다. 튜터 PRD의 입력 가드(FR-02) 요구와 어긋남 |
| D. B + 문장 단위 점진 표시 | B에서 교환 판정을 문장 창마다 실행해 통과한 문장부터 표시 | 첫 문장 ≈ max(J, G₁) + J₁ | 문장 창 수만큼 | 2 | 첫 문장이 빠르다 | 정답 유출·문맥 위반 탐지 약화, 수리 제한, 호출 증가, 꼬리 재검사 필요 |

B와 C는 지연이 같다. B는 저가 호출 1회를 더 써서 **생성 전 차단**, **의도 기반 전환**, **멀티턴 점수 입력**을 얻는다. C는 B의 ablation 설정(입력 판정 끔)으로 그대로 측정할 수 있다. 보고서에 "입력 판정이 차단율·과잉 거절에 기여하는가"를 수치로 넣을 수 있다.

## 4. 제안 구조 (B)

```
학생 메시지
  │
  ▼  [직렬, 코드, 수 ms]
  ① 정규화 → ② 위기 어휘 ─(플래그)─▶ ⑤에 위기 플래그 전달 (같은 호출에서 하위 분류,
            │                          막히는 경우에도 응답은 위기 템플릿, ⑤ 실패 시 T1)
            → ③ 확실한 규칙 ─(확실)─▶ 차단
            → ④ PII 마스킹
  │
  ├──────────────────────────────┐  [병렬 시작]
  ▼                              ▼
  ⑤ LLM 입력 판정                  튜터 검색 → ⑥ 검색 가드(코드) → 튜터 생성
  (현재 메시지 + 최근 턴 요약 + R)    (비스트리밍, 내부 완성까지)
  │                              │
  └──────────── 합류 ─────────────┘
     입력 판정 = 차단(고신뢰)  → 생성 결과 버림, 거절 템플릿
     입력 판정 = 전환·부분 응답 → 생성 결과 버림, 지시를 붙여 재생성 (해당 턴만 지연)
     입력 판정 = 허용          → 계속
  │
  ▼  [직렬]
  ⑦ 코드 검사 (카나리아, 인용 번호, PII, 금지 표현)
  ⑧ LLM 교환 판정 1회 (문장별 근거·인용 + 유해 + 정답 유출)
  ⑨ 수리 (삭제 → 콜백 시 재생성 1회 → 폴백)
  │
  ▼
  표시
```

### 바뀌는 점

| 항목 | PRD v2 | 제안 |
|---|---|---|
| 입력 판정 | 생성 전에 직렬 | 생성과 병렬. 판정이 끝나면 합류 |
| 멀티턴 재판정 | R이 임계를 넘으면 별도 LLM 호출 | **추가 호출 없음**. 입력 판정 프롬프트에 최근 턴 요약과 R을 항상 넣고, R이 높으면 넣는 턴 수를 4 → 8로 늘린다 |
| 차단 권한 | 규칙, 입력 판정, 세션, 코드 검사, 교환 판정 | **결정적**: 규칙(확실한 패턴), 카나리아. **확률적**: 입력 판정 고신뢰 차단, 교환 판정의 유해·유출. 위기 플래그가 있으면 막을 때도 위기 템플릿으로 응답. 근거 위반은 수리 |
| 보정 | 단계별 임계값 | 정상 학생 질문 세트로 **파이프라인 전체** 과잉 거절을 재고, 입력 판정 임계값을 마지막에 맞춘다 |
| 판정 호출 | 2–3회 + R2 | 판정 2회(+R2 재판정 ≤15%, 형식 재요청). 전환 재생성은 생성 호출로 따로 집계 |
| 스트리밍 | 비스트리밍 | P0는 비스트리밍 유지. D(점진 표시)는 P2 실험. 할 경우 꼬리 구간 최종 검사 필수 |
| 장애 시 | GR-14 | 유지. 병렬 쪽 판정이 타임아웃되면 "범주 모름" 규칙 적용(연락처 붙인 안전 응답). 생성은 그대로 두되 교환 판정은 반드시 거친다 |

### 비용과 위험

- **차단 요청의 생성 비용 낭비**: 비율은 입력 판정 차단율과 같다(정상 서비스에서는 낮음, 공격 평가 세트에서는 높음). 평가 예산(GR-15)에 반영한다.
- **전환·부분 응답 턴은 재생성으로 지연**이 생긴다(대략 J + G). 비율은 측정해서 보고한다. 비율이 높으면 의도 신호를 생성 프롬프트에 미리 넣는 방식을 검토한다. 이 방식은 튜터 쪽 결정이다.
- **병렬 경쟁 조건**: 정규화와 PII 마스킹처럼 입력을 바꾸는 단계는 병렬 분기 **전에** 끝낸다(NeMo 경고).
- **엘리스 API 동시성 한도**: 요청당 동시 호출이 2개(판정 + 생성)가 된다. RPM과 동시성을 확인해야 한다(주최측 질문 3번).

### 버린 대안

- **저가 1단 분류기로 입력 LLM 판정 건너뛰기**(OpenAI·Anthropic·Meta의 캐스케이드): 그쪽의 1단은 모델 내부 프로브나 20ms짜리 인코더다. 우리는 API 전용이라 1단도 네트워크 호출이고, 병렬 구조에서는 입력 판정 지연이 이미 숨겨진다. 남는 이득은 비용뿐이라 P2로 둔다(ADR-0002 유지).
- **판정 항목별로 따로 호출**: 호출 수와 지연이 늘어난다. 묶었을 때 정확도가 떨어지는지는 개발 세트 A/B로 확인하고, 떨어지면 근거성만 분리한다.

## 5. 측정할 것 (보고서용)

1. 지연: A(직렬) vs B(병렬)의 p50·p95, 단계별 분해
2. 기여도: B vs C(입력 판정 끔)의 차단율·과잉 거절 → 입력 판정의 순기여
3. 과잉 거절 원인 분해: 어느 차단 계층이 정상 질문을 막았는지
4. 낭비 비용: 차단·전환으로 버린 생성 토큰 비율
5. 묶음 판정 A/B: 교환 판정 1회 vs 근거성만 분리 2회

## 미검증

- 병렬 가드의 실측 지연 절감(공개 수치 없음). 우리 하네스로 잰다.
- 엘리스 API의 동시 호출 허용 여부
- 단일 호출 다중 과제 판정의 정확도 손실
- NeMo 병렬 rail 문서(404, 릴리스 노트로만 확인), CC 1세대 스트리밍 중단 방식(2차 출처)
