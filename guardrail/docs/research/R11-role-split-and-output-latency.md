# R11 · LLM + Jev 역할 분담, 출력 판정 지연, 장애 처리

작성 2026-10-30 · `/ecc:deep-research` (조사 에이전트 3개 병렬) · 대상: R10 구조 B(ADR-0007)

[확인] = 페이지를 직접 읽음, [요약만] = 검색 요약만 봄.

**결론**
- 입력 쪽은 **Jev와 LLM 입력 판정을 생성과 함께 병렬**로 돌린다. Jev는 탈옥·인젝션만 보고 **고신뢰일 때만 차단**한다. 중간 구간은 차단하지 않고 세션 위험 R에 넣는다. 정책·맥락·위기 하위 분류는 LLM만 한다. 둘 중 하나라도 막으면 막는 OR 결합은 쓰지 않는다.
- 출력 쪽 병목(⑧)은 호출 수가 아니라 **출력 토큰**이다. ⑧은 1회로 두되 **실패한 문장만 출력**하게 바꾸고, **코드 사전 필터**가 교재와 거의 같은 문장을 자동 통과시켜 판정할 문장 수를 줄인다. 코드가 자동 실패를 내리지는 않는다.
- 판정이 실패하면 무조건 거절하지 않는다. **결정적 위험 등급**에 따라 나눈다. 위기·확실한 차단은 닫고(fail-closed), 출력 판정 실패는 코드가 확인한 문장만 보여 주는 부분 응답으로 낮춘다.
- 모든 LLM 호출을 **동시성 게이트 하나**로 묶고 재시도 계층을 하나로 둔다. 인프라 때문에 생긴 폴백은 과잉 거절과 **따로 집계**한다.

## 1. Jev: 무엇을 믿을 수 있나

| 항목 | 내용 | 출처 |
|---|---|---|
| 형태 | 생성하지 않는 판정 모델. Choice(보기 ≤255개 중 하나 + 확률), Score(2–10단계), Noul(예/아니오 0–1). `confidence`는 정답 확률이 아니라 확률 분포의 집중도 | [확인] https://www.noze.it/en/insights/jev-system-one-typed-decisions/ |
| 언어 | 주로 영어로 학습, 다른 언어는 정확도가 낮다고 명시 | 같은 출처 |
| 지연·단가 | 회사 주장 70–500ms, 입력 $0.042/1M 토큰, 출력 무료. 독립 검증 없음 | 같은 출처 |
| 접근 | 대기 명단. Vercel AI Gateway `typesafe-ai/jev-1.14.0`(10/15), 요청별 무보존 설정 가능. Netlify AI Gateway에도 있음. Cloudflare는 확인 못 함 | [확인] https://vercel.com/changelog/typesafe-ais-jev-1-14-is-now-available-on-ai-gateway · [요약만] https://www.netlify.com/changelog/typesafe-jev-ai-gateway/ |
| 약점 | 날짜 비교·세기에 약함, 질문 문구와 적대적 입력에 민감, 부정형 질문과 확률이 상보적이지 않을 수 있음, **미국 서버에서 처리** | [확인] https://motherduck.com/docs/integrations/data-science-ai/typesafe/ |
| 인젝션 벤치마크 | 경쟁사(Lasso) 측정, 오탐률 0.23% 고정: 전체 재현율 76.2%, **"이전 지시 무시" 문구가 있는 공격 99.8% / 없는 공격 63.4%**, 인코딩·난독화 76%, p95 526ms. 무해한 뒤집힌 글자의 94%를 공격으로 표시. 버전·언어 미기재 | [확인] https://www.lasso.security/blog/lasso-vs-jev-can-jev-really-replace-a-prompt-injection-classifier |
| 근거 판정 | 문장 + 청크를 넣고 3지선다로 만들 수는 있다. 벤치마크는 없음 | Vercel 변경 기록의 "verification" 용례만 |

**해석**
- Jev는 노골적인 공격 문구를 매우 잘 잡고, 돌려 말한 공격은 놓친다. 그래서 **"고신뢰 차단기"** 자리에 맞고 단독 탐지기로는 맞지 않는다. 돌려 말한 공격은 LLM 입력 판정이 맡는다.
- 이상한 서식에 반응하는 성질이 있다. 우리는 정규화본(ADR-0001)을 보내서 이 오탐을 줄인다. 한국어에서도 그런지는 직접 재야 한다.
- 근거 판정에는 쓰지 않는다. 인용문을 돌려주지 않고(ADR-0005), 벤치마크도 없다.

## 2. 가드 여러 개를 합치는 규칙

| 근거 | 내용 | 출처 |
|---|---|---|
| OR 결합의 오탐 누적 | 독립 가정에서 합친 오탐률 = 1 − Π(1 − FPR_i). 겹친 구조의 과잉 거절 7.8% → 단계적 대응으로 2.9% | [요약만] https://arxiv.org/abs/2603.29062 |
| 겹치면 빈틈은 줄지만 안 닫힘 | 2번째 계층이 미탐을 44% → 24%로 | [요약만] https://arxiv.org/html/2608.08641v1 |
| 가드마다 실패 방향이 다름 | 가드 모델 18개 중 과잉 차단형과 과소 차단형이 갈림 → 오류가 독립이 아님 | [요약만] https://arxiv.org/pdf/2608.24232 |
| Anthropic CC++ | 값싼 1단은 차단 없이 올리기만, 2단에서 점수 평균. WildChat 거절 0.1%에 맞춰 임계값 보정 | [요약만] https://arxiv.org/pdf/2601.04603 |
| Azure Prompt Shields | "탐지됨"만 알려 주고 조치는 앱이 정함. 오탐이 나오면 차단 대신 주석 모드를 권장 | [확인] https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection |
| 임계값 정하기 | 가드 전용 conformal·Neyman-Pearson 논문은 못 찾음. 실무 방법은 정상 데이터에서 목표 오탐률에 맞춰 정하고 다른 정상 세트로 확인 | Lasso 글, [요약만] https://arxiv.org/pdf/2604.16542 |

**해석**: OR 결합은 과잉 거절을 쌓는다. AND 결합은 미탐을 쌓는다. 역할을 나누고 한쪽(Jev)에만 **높은 임계값의 단독 차단권**을 주는 방식이 둘 다 피한다. 중간 구간은 차단 대신 신호(R)로 쓴다. 이것이 CC++의 "1단은 올리기만" 원칙과 같다. 다만 Jev와 LLM 판정이 동시에 돌기 때문에 같은 턴의 LLM 판정에 Jev 신호를 넣을 수는 없다. 그래서 중간 구간 신호는 R을 통해 **다음 턴부터** 반영된다.

**Jev 대체 후보(한국어)**: Kakao Kanana Safeguard-Prompt 2.1B(Apache-2.0, 인젝션 A1·유출 A2, 단일 토큰 출력). 자체 한국어 세트 F1 0.844, 정밀도 0.968, 재현율 0.748. 비교값은 GPT-4o 0.804, Prompt Guard 2 86M 0.751. 회사 자체 측정이고, 자체 호스팅이 필요하다. [확인] https://huggingface.co/kakaocorp/kanana-safeguard-prompt-2.1b. Prompt Guard 2는 평가 언어 8개에 한국어가 없다. [확인] https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M

## 3. 출력 판정(⑧) 지연 줄이기

| 근거 | 내용 | 출처 |
|---|---|---|
| 지연 구성 | 전체 ≈ 첫 토큰 시간 + 출력 토큰 × 토큰당 시간. 캐시는 첫 토큰 시간만 줄인다 | [요약만] https://www.truefoundry.com/glossary/time-to-first-token |
| 추론 끄기 | 비추론 소형 모델의 첫 토큰 약 1.1s, 추론형은 5–19s (시점 스냅샷) | [요약만] https://artificialanalysis.ai/models/comparisons/gemini-3-1-flash-lite-preview-vs-claude-4-5-haiku |
| 프롬프트 캐시 | 고정 접두부(지시·정책)에만 효과. 청크는 요청마다 바뀜 | [요약만] https://humanloop.com/blog/prompt-caching |
| 병렬 분할 | 문장별로 쪼개 병렬 호출하는 설계는 흔하지만 단일 호출과 비교한 측정은 없음. 쪼갤수록 꼬리 지연과 호출 제한이 나빠짐 | [요약만] |
| 소형 검증 모델 | Bespoke-MiniCheck-7B(비상업), HHEM-2.1-Open(영어 전용), LettuceDetect(한국어 없음), Granite Guardian(영어 전용), Azure 근거성(영어, 2027-04 종료). **한국어 지원 API는 Vectara HHEM-2.3뿐**, 지연 수치 없음 | [확인] https://huggingface.co/vectara/hallucination_evaluation_model 외 |
| 한국어 어휘 비교 | 문자 단위보다 형태소 단위가 사람 판단과 더 맞음. ROUGE식 겹침은 한국어에 잘 안 맞음 | [요약만] https://aclanthology.org/2022.humeval-1.1.pdf · https://arxiv.org/pdf/2005.03510 |
| 2단 검증 | 일부만 검증기로 보내도 탐지 성능 유지, 다만 값싼 1단은 추론 오류를 놓침 | [요약만] https://arxiv.org/pdf/2502.15845.pdf · https://arxiv.org/pdf/2604.25634 |

**한국어 문장 단위 근거 판정의 지연을 잰 공개 자료는 찾지 못했다.** 목표치는 우리 하네스로 직접 잰다.

**해석**
- 지금 ⑧은 문장마다 라벨과 80자 인용을 내서 출력이 답변 길이에 비례한다. **실패 문장만 출력**하면 정상 답변에서는 출력이 몇 토큰으로 준다. 이게 가장 큰 효과다.
- 코드 사전 필터는 **자동 통과만** 한다. 교재 청크와 거의 같은 문장(문자 3-gram 포함률 ≥θ, 숫자·라틴 용어가 모두 그 청크에 있음)은 판정하지 않고 SUPPORTED로 둔다. 애매한 문장은 모두 LLM에 보낸다. 형태소 분석기는 문자 3-gram이 부족하다고 측정될 때만 넣는다.
- ⑧을 둘(유해·유출 / 근거)로 쪼개는 것은 보류한다. 출력이 짧아지면 쪼개서 얻는 이득이 작고, 호출 제한 압박은 커진다.

## 4. 장애 처리와 부하

| 근거 | 내용 | 출처 |
|---|---|---|
| 호출 제한 | 토큰 버킷. 짧은 폭주는 한도를 넘고, 급증 자체를 막는 제한도 있음. `retry-after`가 대기 시간 | [확인] https://platform.claude.com/docs/en/api/rate-limits |
| 재시도 | `Retry-After`는 최소 대기. 없으면 지수 백오프 + 지터, 횟수·총시간 상한. 실패 요청도 한도에 셈. **자체 재시도를 쓰면 SDK 재시도는 끈다**. `max_tokens`를 실제 크기에 맞춘다 | [확인] https://developers.openai.com/api/docs/guides/rate-limits.md |
| 재시도 위치 | 스택에서 한 곳에서만, 재시도 예산(토큰 버킷), 항상 지터 | [확인] https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter |
| 대체 모델 | LiteLLM: 모델 그룹 안에서 재시도 후 다음 그룹으로, 실패 배포는 잠시 제외 | [확인] https://docs.litellm.ai/docs/proxy/reliability |
| 헤지 요청 | p95 넘으면 예비 요청. 429가 병목이면 폭주를 키워서 우리에게 안 맞음 | [요약만] https://blog.acolyer.org/2015/01/15/the-tail-at-scale/ |
| 실패 시 열기/닫기 | OpenAI Guardrails 기본은 실패 시 통과(fail-open), 플래그로 닫기. 검사별·위험도별로 따로 정하라는 권고 | [확인] https://openai.github.io/openai-guardrails-python/quickstart · [요약만] https://www.truefoundry.com/fr/blog/truefoundry-ai-gateway-guardrails-explained |
| 평가 도구 | promptfoo: 429면 동시성 절반, 성공이 이어지면 +1(AIMD), 남은 한도 10% 미만이면 미리 줄임 | [확인] https://www.promptfoo.dev/docs/configuration/rate-limits/ |
| 재시도 폭풍 | 429를 한꺼번에 재시도하면 원래 요청과 부딪힌다. 동시성 게이트로 해결 | [요약만] |

**가용성 지표 표준은 찾지 못했다.** 직접 정의한다: `fallback_infra`(인프라 때문에 폴백) 비율을 판정기 차단과 따로, 정상/공격별로 보고한다.

## 5. 제안 구조 (구조 B2)

```
학생 메시지
  ▼ [직렬, 코드, ≤50ms]  ① 정규화 → ② 위기 어휘 → ③ 확실한 규칙 → ④ PII 마스킹
  ├──────────────┬──────────────┐  [동시에, 모두 동시성 게이트 통과]
  ▼              ▼              ▼
  Jev           ⑤ LLM 입력 판정   [튜터] 검색 → ⑥ → 생성
  (탈옥·인젝션)   (정책·맥락·위기 하위 분류)
  └──────── 합류 ───────────────┘
     Jev ≥ τ_J → 차단 / τ_m ≤ Jev < τ_J → 차단 안 함, R에 반영
     그 외는 ⑤ 판정대로(차단·전환·부분·허용·위기). 위기 플래그가 있으면 막을 때 위기 템플릿
  ▼ [직렬]
  ⑦ 코드 검사 → 사전 필터(자동 통과만) → ⑧ LLM 교환 판정 1회(실패 문장만 출력) → ⑨ 수리 → 표시
```

| 결정 | 내용 |
|---|---|
| 판정 호출 | LLM 2회(⑤, ⑧) + Jev 1회(켰을 때). 요청당 동시 호출 3개(생성 + ⑤ + Jev) |
| 차단 지점 | 4곳 유지. ⑤ 자리의 확률적 차단은 "LLM 고신뢰 또는 Jev 고신뢰" |
| Jev 임계값 | τ_J는 한국어 정상 학생 질문 ≥300건에서 오탐 ≤0.5%가 되도록 정하고, 다른 정상 세트로 확인한다. τ_m은 개발 세트에서 정한다 |
| Jev 입력 | 정규화·마스킹을 마친 현재 메시지만. 대화 기록과 학생 정보는 보내지 않는다 |
| ⑧ 출력 | 유해·유출 플래그 + 실패 문장 `{i, label, quote≤80}` 목록. 모두 통과면 `[]`. 비추론 저가 모델, 구조화 출력, 고정 접두부를 앞에 둬 캐시 |
| 사전 필터 | 문자 3-gram 포함률 ≥θ(출발 0.9) **그리고** 숫자·라틴 용어가 그 청크에 모두 있음 → SUPPORTED(인용은 코드가 고른 구간). θ는 라벨 단 한국어 문장 ≥200건에서 자동 통과가 미탐을 하나도 늘리지 않는 값으로 정한다 |
| 인용 확인 | 인용과 청크 모두 `normalize()` 후 공백을 지우고 비교 |
| 동시성 | 모든 LLM 호출(생성 포함)을 세마포어 + AIMD 게이트 하나로. 재시도는 그 한 곳에서만, `retry-after` 준수, 지터, 호출별 마감 안에서. SDK 재시도는 끔 |
| R2 재생성 | 지연이 측정되기 전까지 기본 끔 |

**판정 실패 등급(재시도까지 실패한 뒤)**

| 상황 | 동작 | 근거 |
|---|---|---|
| 위기 플래그 | 위기 템플릿(변경 없음) | 결정적, LLM 성공에 기대지 않음 |
| ③·⑦ 결정적 차단 | 차단(변경 없음) | |
| Jev 실패 | ⑤ 판정만으로 진행 | 역할 분담이라 서로 백업 |
| ⑤ 실패 | Jev 고신뢰면 차단, 아니면 허용으로 진행. ⑧이 유해·유출을 다시 본다 | 입력 정책은 실패 시 통과(fail-open), 뒤에 ⑧이 있음 |
| ⑧ 실패 | 사전 필터가 자동 통과시킨 문장만 + "교재에서 확인한 부분만 보여 줄게요". 그런 문장이 없으면 학습 안내 안전 응답 | 확인 안 된 내용은 닫고(fail-closed), 확인된 부분은 보여 줌 |

**지연 예산(추정)**: 코드 ≤50ms + 검색·생성 2–4s + ⑧ 약 1–1.5s(실패만 출력, 비추론 모델) ≈ 3–5.5s. 첫 문장 p95 ≤5s는 여전히 빠듯하다. 문장 단위 점진 표시(구조 D)는 P2로 남긴다.

## 6. 남은 공백
- Jev의 한국어 성능, 한국어 인젝션 독립 벤치마크: 없음. 개발 세트에서 LLM 단독 / Jev 단독 / 역할 분담을 비교한다(돌려 말한 공격, 인코딩 공격 포함).
- 한국어 문장 단위 근거 판정 지연: 공개 자료 없음. 하네스로 잰다.
- 엘리스 게이트웨이의 호출 한도·동시성·대체 모델: 알 수 없음. 평가 전에 실제 게이트웨이로 폭주 시험(수백 건, 동시성 20–50)을 한다.
- Portkey·OpenRouter·Vercel 게이트웨이 장애 처리, OpenAI 캐스케이드·NeMo 결합 문서: 읽지 못함.
