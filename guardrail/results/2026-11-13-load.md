# S2.10 부하 시험: 동시 64 · 600요청

작성 2026-11-13 · 담당 danielcho02 · 계획: C2 §S2.10, PRD GR-10·GR-09, SPEC §3

채점기와 같은 모양(동시 64, 요청당 30초 제한)으로 가드 서버에 600요청을 보낸 결과다. 채점은 하지 않았다.

## 실행

| 항목 | 값 |
|---|---|
| 어디서 | 런박스(CPU 8개, 스레드 풀 12), 서버와 부하 도구가 같은 기계. `uvicorn guardrail.server:app` 단독(튜터 호출 없음) |
| 코드 | `gr/s2.10-load` `bb06ac3`(로컬 브랜치, 푸시 안 함). 설정 6.0.2(`cba7a73b6986`): 토큰 상한 1600, 게이트 64, `read` 12초, 재시도 1, 예산 20초 |
| 요청 | 홀드아웃을 뺀 가드 160행을 돌려 600개(고정 시드로 섞음). 후보 답변이 있는 요청 241개 |
| 1차 | 600건 그대로 |
| 2차 | 같은 600건 중 5개의 이력을 약 1MB로 부풀림. 서버는 1차에 이어 그대로 |
| 도구 | `python -m guardrail.eval.load`. 기본값으로 떨어진 판정은 서버 접근 로그의 오류 칸에서 센다 |
| 호출 | 1차·2차 각 841회 이하(입력 600 + 출력 241) + 재시도 + probe. 합계 약 1,700회 이하, 오늘 누적 약 10,200회 이하(서버는 호출 수를 세지 않아 상한이다) |

## 판정

| 질문 | 판정 | 근거 |
|---|---|---|
| 30초 안에 모두 끝나는가 | **통과** | 1,200건 중 시간 초과 0, 최대 13.6초 |
| 지연이 목표 안인가 | **p95 목표 미달**(9.2–9.4초 대 8초). 전체 시간은 통과 | 규격의 30초에는 여유가 크다. 8초는 팀이 정한 목표다 |
| 기본값으로 떨어진 비율 | **통과, 다만 1차는 기준에 가깝다** | 출력 1.7%·0.4%, 입력 0%. 5건 모두 오류 코드가 역할 이름뿐이라 마감 초과인지 재시도 뒤 실패인지 가르지 못한다 |
| 긴 요청이 남을 막는가 | **통과** | 1MB 5개를 섞어도 나머지의 p95가 9.15 → 9.37초, 시간 초과 0 |
| 런박스 KB 검색 | **통과** | p95 0.82ms |

- 동시 16에서 64로 올리면 p50이 2.3–3.0초 → 4.6–4.7초가 된다. 느려진 곳이 nano 쪽인지 서버 안(게이트 대기, 준비 단계의 스레드 풀 대기)인지는 이 시험으로 가를 수 없다. 서버 로그는 요청 전체 시간만 남긴다.
- 출력 판정 실패 1.7%와 0.4%는 같은 조건의 두 실행이다. 두 값의 차이는 잡음으로 본다. 한 번 더 재면 2%를 넘을 수 있다.

## 이 시험이 말하지 않는 것

- **튜터와 함께 받는 부하.** 실제 채점은 가드 약 300 + 튜터 약 300이 같은 키로 동시에 간다. 여기서는 가드만 600건이라 nano 호출 수는 비슷하지만 튜터의 긴 생성 호출이 없다. 통합 서버에서의 값은 이보다 나쁠 수 있다.
- **점수.** 응답 내용은 채점하지 않았다.
- **429.** 서버는 실패 사유를 역할 단위로만 남겨 속도 제한이 있었는지 알 수 없다. 실패가 5/482건이라 있었다 해도 드물다.

## 결론과 다음

- 동시 64에서 가드 단독은 규격(30초, 형식)을 지키고 실패율도 기준 안이다.
- p95가 목표 8초를 1.2–1.4초 넘는다. 규격 위반이 아니고 점수에 닿지 않으므로 지금 설정을 바꾸지 않는다. 손보려면 느려진 곳부터 가려야 한다(역할별 호출 시간과 게이트 대기 시간을 로그에 남기는 것이 먼저).
- 출력 판정 실패가 2%에 가깝다. 통합 서버에서 넘으면 ADR-0014에 남겨 둔 다음 순서(`kb_quote`를 뺀다) 또는 출력 호출의 `read` 한도를 본다.
- 도구의 흠 하나를 고쳤다: 접근 로그 집계가 401 줄(서버가 떴는지 보려고 보낸 요청)을 역할로 셌다. 200인 줄만 세게 했다(`78ea32b`). 위 표의 값은 영향이 없다.
