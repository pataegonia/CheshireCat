# 출력 판정 프롬프트 v1 단독 실측 3회 (S2.7, R14-D2)

작성 2026-11-13 · 담당 danielcho02 · 근거 계획: [R14 §6](../docs/research/R14-prompt-uplift.md#6-council-2026-11-13-후보-선별) R14-D2·D3·D4·D8

출력 근거 판정 nano(`output_judge.md` version 1)만 따로 잰 기준선이다. 입력 범주는 재지 않았다.

## 실행

| 항목 | 값 |
|---|---|
| 어디서 | 런박스(`openai/gpt-5-nano`, `reasoning_effort: low`, `max_completion_tokens: 800`, json_schema strict) |
| 명령 | `python -m guardrail.eval.run --config configs/default.yaml --output-only --name out-v1 --repeat 3` |
| 코드 | `gr/s2.7-output-judge` `43d0e84`(로컬 브랜치, 푸시 안 함) |
| 판정기 | `OutputOnlyGuard`: BM25 검색 → 문맥(1위 섹션 전체 + 다른 섹션 조각, R14-D4) → `ask_grounded`. 입력은 상수(`normal`). 규칙 ②와 조립은 타지 않는다. 실패하면 근거 있음으로 두고 오류로 센다 |
| 데이터 | 홀드아웃을 뺀 가드 행 가운데 후보 답변이 있는 64행: block 범주 13(정답 grounded=true, safe=false), non-block 51(근거 있음 23, 근거 없음 28) |
| 호출 | 회당 64 + probe 5. 합계 197회. 오늘 누적 4,009회 |
| 분석 | `scripts/r14/output_run_analysis.py`(`gr/s2.7-output-judge` `d4d8e33`, 호출 없음) |

보고서의 가드 점수·block F1은 입력이 상수라 뜻이 없다. 아래는 저장된 nano 응답을 정답 라벨과 맞댄 것이다.

## nano의 "근거 없음" 판정 (non-block 51행)

| 지표 | 1회차 | 2회차 | 3회차 |
|---|---|---|---|
| 근거 없음 판정 수 | 19 | 19 | 21 |
| 그중 정답도 근거 없음(정밀도) | 19 (**1.000**) | 19 (**1.000**) | 21 (**1.000**) |
| 답이 온 행만의 재현율 | 0.731 (19/26) | 0.731 (19/26) | 0.778 (21/27) |
| 실패를 놓침으로 센 재현율(근거 없음 28행) | 0.679 | 0.679 | 0.750 |
| 규칙 ②가 안 걸린 행의 재현율 | 0.600 (9/15) | 0.714 (10/14) | 0.688 (11/16) |

- **잘못 잡은 것이 없다.** 근거 있음 23행 × 3회 = 69번 판정에서 "근거 없음"이 0번이다. 다만 23행이라 실제 오탐률의 95% 상한은 약 13%다(0/23).
- 놓침이 문제다. 근거 없음 28행 가운데 6행은 3회 모두 놓쳤다(그중 1행은 규칙 ②가 잡는다).
- 실행 사이에 판정이 바뀌거나 실패가 섞인 행은 7/51이다.

## 인용 (R14-D2)

| 지표 | 1회차 | 2회차 | 3회차 |
|---|---|---|---|
| `answer_quote`가 답변의 부분 문자열(8자 이상) | 19/19 | 19/19 | 21/21 |
| `kb_quote`가 문맥의 부분 문자열 | 14/19 | 15/19 | 15/21 |
| `kb_quote`를 비움 | 1 | 1 | 1 |
| 확인된 `answer_quote`를 구간으로 낼 때 구간 F1 평균 | 0.597 | 0.605 | 0.622 |

- `answer_quote`는 59번 모두 답변에서 그대로 옮겼다. `quote_min_chars` 8과 1의 결과가 같다.
- `kb_quote`는 4번에 1번꼴로 문맥과 글자가 다르다. `tier3_trust: both_quotes`로 하면 재현율이 0.54–0.58로 떨어지고 정밀도는 그대로다(이미 1.000). **`both_quotes`는 쓸 이유가 없다.**
- `all`과 `answer_quote`는 이 자료에서 결과가 같다.

## 조립 방식별 출력 평균 (호출 없이 계산)

64행, 범주는 정답을 썼다(입력 오류를 뺀 값). block 행은 ①(true / [] / safe=false), 실패는 근거 있음.

| 조립 | 1회차 | 2회차 | 3회차 | grounded | 구간 F1 |
|---|---|---|---|---|---|
| 규칙 ②만 (nano 없음) | 0.811 | 0.811 | 0.811 | 0.750 | 0.684 |
| ② → ③ 구간 없음 (**지금 설계**, ADR-0014) | 0.858 | 0.863 | 0.869 | 0.891–0.922 | 0.684 |
| ② → ③ 확인된 `answer_quote`를 구간으로 | **0.892** | **0.899** | **0.909** | 0.891–0.922 | 0.786–0.804 |
| ③ 인용 먼저 → ② | 0.884 | 0.893 | 0.899 | 0.891–0.922 | 0.760–0.776 |

- 규칙 ②는 non-block 12행에 걸렸고 12행 모두 정답이 근거 없음이다.
- nano ③을 붙이면 출력 평균이 0.811 → 0.858–0.869로 오른다.
- **③에서 `answer_quote`를 구간으로 내면 0.892–0.909다.** 지금 설계(0.858–0.869)와 범위가 겹치지 않는다. 가드 점수로는 약 +1.5–1.8점(출력 가중 0.45)이다. ADR-0014는 ③이 구간을 내지 않는다고 정했으므로 이것은 설계 변경이다(미결정).
- 같은 3회 응답에 조립만 바꿔 계산한 것이라 세 값의 차이는 독립 표본의 차이가 아니다. 64행짜리 추정이다.
- 위험: nano가 근거 있는 답을 근거 없음으로 잘못 잡으면, 구간을 낸 쪽은 그 행의 구간 F1도 0이 된다(빈 구간이면 1). 이번에는 그런 행이 없었다.
- 둘 다 걸린 행에서는 규칙 ②의 구간이 nano 인용보다 낫다(② 먼저가 0.008–0.010 높다).

## 실패 (R14-D8)

| 항목 | 값 |
|---|---|
| 실패 | 3 · 2 · 4 / 64, 합계 9/192 = **4.7%** |
| 원인 | 8건은 `finish_reason=length`(숨은 추론 토큰이 `max_completion_tokens` 800을 넘겨 JSON이 잘림, 4.2%), 3회차의 1건은 `bad_request` |
| 실패한 행 | 7행. 문맥 1,955–4,735자, 답변 23–113자. 긴 문맥에만 몰리지 않았다 |
| 지연 | 320행 전체 p95 4.2 · 4.6 · 6.3초(256행은 호출이 없어 0이므로 호출 64행의 75번째 백분위쯤이다). 호출만의 p95는 이 실행에 남지 않았다 |

- R14-D8의 기준(역할별 실패 2%)을 넘는다. 전체 실행(S2.9) 전에 출력 판정의 토큰 상한부터 고쳐야 한다.
- 실패한 7행 중 3행이 근거 없음 행이라 실패가 그대로 놓침이 된다.

## 3회 모두 놓친 6행

6행 모두 **어긋나는 자료 구절이 nano에 준 문맥 안에 있었다.** 검색이나 문맥 길이 문제가 아니다.

| 어긋난 종류 | 행 수 |
|---|---|
| 단계 이름 하나가 바뀜(3단계의 마지막 이름) | 2 |
| 항목이 하나 더 붙고 개수가 바뀜(세 단계 → 네 단계) | 1 |
| 비교 대상이 바뀜(자료 → 다른 것) | 2 |
| 코드 동작 설명이 반대(같은 길이 → 고정 개수) | 1 (규칙 ②가 잡음) |

답변 대부분이 자료와 같고 낱말 하나나 항목 하나만 다른 경우다. effort low의 nano가 이런 차이를 놓친다.

## `refuses` (R14-D3)

- block 13행은 정답 safe가 모두 false이고 nano는 `refuses=false`를 9–12번, `true`를 1번 냈다. non-block 51행은 safe가 모두 true이고 `refuses=true`는 3회 합쳐 1번이다.
- 이 64행에서 safe 라벨은 "범주가 block인가"와 완전히 같다. `refuses`로 가를 행이 없다. 기록만 하는 지금 결정(R14-D3)을 바꿀 근거가 없다.

## 정리

- nano의 근거 없음 판정은 믿을 만하다(정밀도 1.000, 표본 23행). `tier3_trust`는 `answer_quote`면 충분하고 `both_quotes`는 손해다.
- 약점은 재현율 0.68–0.75와 실패 4.7%(잘림 4.2%)다.
- ③에서 확인된 `answer_quote`를 구간으로 내면 출력 평균이 약 0.035 오른다. ADR-0014 변경이 필요하다.
- 토큰 상한을 올리면 잘림이 사라지고 재현율이 0.82로 오른다(아래, 1회씩이라 확인 전).

## 토큰 상한 선별 (1회씩, R14-D8)

규칙 확인: SPEC §7.1은 "추론 수준(`reasoning_effort`)·최대 출력 토큰·temperature는 API가 받는 범위에서 자유롭게 정합니다"라고 한다. 상한을 올려도 호출 수는 그대로다. 걸리는 것은 요청당 30초와 전체 채점 시간(SPEC §3)뿐이다.

같은 코드·프롬프트에 `--set llm.max_completion_tokens=<값>`만 바꿔 1회씩 쟀다(`out-v1-t1200`, `out-v1-t1600`, 호출 138회, 오늘 누적 4,147회).

| 지표 | 800 (3회) | 1200 (1회) | 1600 (1회) |
|---|---|---|---|
| 실패 | 3 · 2 · 4 / 64 (length 8, bad_request 1) | 1/64 (timeout, 문맥이 가장 긴 4,735자 행) | **0/64** |
| `finish_reason=length` | 4.2% (8/192) | 0% | 0% |
| "근거 없음" 정밀도 | 1.000 | 1.000 (23/23) | 1.000 (23/23) |
| 재현율(실패를 놓침으로 셈, 28행) | 0.679–0.750 | 0.821 | 0.821 |
| `answer_quote` 확인(8자) | 59/59 | 22/23 | 23/23 |
| 출력 평균: ② → ③ 구간 없음(지금 설계) | 0.858–0.869 | 0.874 | 0.879 |
| 출력 평균: ② → ③ 인용을 구간으로 | 0.892–0.909 | 0.915 | 0.928 |
| 320행 전체 지연 p95(호출 64행의 75번째 백분위쯤) | 4.2–6.3초 | 4.95초 | 5.38초 |

- 800에서 잘리던 호출이 답을 내면서 놓침이 줄었다. 두 값 모두 800의 3회 범위 위에 있다. 다만 **1회씩이라 채택 기준(3회 범위가 겹치지 않음)은 아직 못 채웠다.**
- 1200과 1600의 차이는 1행이라 가를 수 없다. 1200의 실패 1건은 잘림이 아니라 읽기 한도 12초를 넘긴 것이다. 상한을 올리면 잘리던 호출이 더 오래 돈다는 뜻이다.
- 지연은 800의 범위(행 p95 4.2–6.3초) 안이다. 호출만의 p95와 동시 64에서의 지연은 이 실행으로 알 수 없고 부하 시험(S2.10)에서 본다.
- 3회 모두 놓치던 6행 중 5행은 상한을 올려도 놓친다. 낱말 하나가 바뀐 답변을 놓치는 문제는 토큰 상한으로 풀리지 않는다.
- `llm.max_completion_tokens`는 입력 판정에도 같이 적용되는 값이다. 입력 판정은 800에서 잘림이 0이었다.

## 1600 확인 3회

1600을 2회 더 쟀다(`out-v1-t1600-r2`, `--repeat 2`, 호출 133회, 오늘 누적 4,280회). 위 선별의 1회와 합쳐 3회다.

| 지표 | 800 (3회) | 1600 (3회) | 범위가 겹치는가 |
|---|---|---|---|
| `finish_reason=length` | 4.7% · 3.1% · 4.7% | 0% · 0% · 0% | 안 겹침 |
| 실패 | 3 · 2 · 4 / 64 (합 4.7%) | 0 · 0 · 2 / 64 (합 **1.0%**, 2건 모두 timeout) | 2에서 닿음 |
| 재현율(실패를 놓침으로 셈, 28행) | 0.679 · 0.679 · 0.750 | 0.821 · 0.821 · 0.821 | **안 겹침** |
| "근거 없음" 정밀도 | 1.000 · 1.000 · 1.000 | 1.000 · 0.958 · 1.000 | 겹침 |
| grounded 정확도(64행) | 0.891 · 0.906 · 0.922 | 0.953 · 0.922 · 0.922 | 0.922에서 닿음 |
| 출력 평균: ② → ③ 구간 없음(지금 설계) | 0.858 · 0.863 · 0.869 | 0.879 · 0.869 · 0.869 | 0.869에서 닿음 |
| 출력 평균: ② → ③ 인용을 구간으로 | 0.892 · 0.899 · 0.909 | 0.928 · 0.902 · 0.910 | 겹침 |
| 320행 전체 지연 p95 | 4.2 · 4.6 · 6.3초 | 5.4 · 7.0 · 5.5초 | 겹침 |

- **잘림은 없어졌다.** 실패는 4.7% → 1.0%로 R14-D8의 2% 기준 아래다. 다만 3회차는 timeout 2건(3.1%)이라 회차 하나만 보면 기준을 넘는다. 잘리던 호출 일부가 읽기 한도 12초까지 가서 끊긴다.
- **재현율은 올랐다**(0.68–0.75 → 0.82, 3회 모두 23/28).
- **출력 평균의 이득은 확인하지 못했다.** 지금 설계 기준 0.858–0.869 → 0.869–0.879로 범위가 0.869에서 닿는다. 채택 기준(범위가 겹치지 않음)을 못 채운다. 평균 차이는 약 +0.009이고 가드 점수로 +0.4점쯤이다.
- **지연은 조금 느는 쪽이지만 범위가 겹친다.** 행 p95가 4.2–6.3초 → 5.4–7.0초다. 동시 64에서의 지연은 부하 시험(S2.10)에서 봐야 한다.
- 처음으로 오탐이 1건 나왔다(2회차). 자료의 항목 한 줄에서 뒷부분을 빼고 옮긴 답변을 nano가 근거 없음으로 잡았고 정답은 근거 있음이다. 800의 3회에는 없던 종류다. "인용을 구간으로" 방식은 이런 행에서 구간 점수까지 잃는다.
- 5회(800 3회 + 1600 3회 중 실패가 아닌 판정) 내내 놓친 근거 없음 행은 4행이다. 낱말 하나가 바뀐 답변이다.

판단: 1600은 "잘림 실패를 2% 아래로"라는 R14-D8의 목적은 채운다. 점수 이득은 잡음 안이다. `default.yaml`을 1600으로 바꿀지는 부하 시험의 지연을 보고 정한다(아직 안 바꿈. 바꾸려면 master-plan §4.4를 먼저 고친다).
