## 판정

채택 기준은 미리 정한 대로다: 후보의 3회 범위가 기준의 범위와 겹치지 않고 높다(닿으면 겹침). 비교 지표는 가드 점수.

| 질문 | 판정 | 근거 |
|---|---|---|
| default가 nano 단독보다 높은가(C2 관문) | **통과, 다만 0.30점 차이** | 79.89 대 79.59. block 판정 한 행이 약 0.3–0.4점이라 한 행에 걸린 결과다 |
| `max_completion_tokens` 1600 | **채택**(실패율 기준) | 출력 호출 실패 6.2–9.4%(전부 잘림) → 0/192. 2% 기준(R14-D8)을 3회 모두 넘던 것이 없어졌다. 이 0/192는 조합 3회만의 값이다. 뒤에 잰 합친 코드 6회는 시간 초과로 8/384(2.1%)다(아래 "출력 판정 호출의 지연과 토큰") |
| `nano_span` 켬 | **가드 점수로는 확인 못 함. 출력 지표로는 나음** | 가드 점수 83.68–84.84가 A와 겹친다. 출력 평균은 0.827–0.837 → 0.889–0.899로 겹치지 않는다. 구간 F1 0.684 → 0.793–0.806 |
| `knn_fewshot` 끔 | **채택 안 함** | block F1 0.805–0.843이 A(0.783–0.876)와 겹치고 범주 정확도는 조금 낮다(겹침) |

- **default의 우위는 전부 출력 쪽에서 나온다.** 출력 평균 +0.10(약 4.6점). block F1은 A와 B가 완전히 겹친다. kNN 예시·kNN 다수·LR이 입력 판정을 nano 단독보다 낫게 한다는 근거는 이 실측에 없다.
- **조합의 이득(+약 2.8점)도 전부 출력 쪽이다.** 가드 점수에서 출력 항을 뺀 값은 조합 43.2–44.8, default 42.7–47.2로 겹친다.
- 조합에서 `nano_span`과 토큰 상한이 둘 다 출력에 작용해 둘의 몫을 가를 수 없다. 구간 F1이 오른 것은 `nano_span`, 실패가 없어진 것은 토큰 상한으로 읽는 것이 자연스럽지만, ③에 닿는 행 수도 10–11 → 12–16으로 늘어 일부는 경로가 바뀐 효과일 수 있다.
- **입력 few-shot의 앞선 결과는 재현되지 않았다.** 입력 단독 실측에서 "예시 없음 0.809–0.854 대 v1 0.771–0.805"로 0.004 차이로 안 겹친다고 적었는데, 이번에 예시가 있는 default가 0.876까지 나왔다. 그때의 차이는 잡음 안이었다고 본다.

## 잡음

| 항목 | 값 |
|---|---|
| 같은 설정 안의 가드 점수 폭 | A 4.75점, B 3.91점, C 1.16점 |
| 같은 설정 안의 block F1 폭 | A 0.093, B 0.074, C 0.038 |
| 3회 사이에 block 판정이 바뀐 행(320행 중) | A 22, B 23, C 29 |
| 출력 평균 폭 | 약 0.01 |

- 가드 160행 × 3회로는 입력 쪽 차이가 block F1 약 0.08(10행쯤) 이상이어야 가려진다. 지금 시험한 입력 변경은 모두 그보다 작다.
- 출력 평균은 폭이 0.01이라 0.02쯤의 차이도 가려진다.

## 결론과 다음

- `max_completion_tokens`를 1600으로 올린다(문서 먼저 → `default.yaml`).
- `knn_fewshot`은 그대로 켠다.
- `nano_span`은 가드 점수 규칙으로는 못 채웠지만 출력 지표가 분명히 낫다. 조합의 몫을 가를 수 없는 경우라 결정을 사용자에게 올린다. 가르려면 출력 단독(1600, `nano_span` 켬 대 끔, 3회씩, 약 390회 호출)이면 된다.
- 내리면 안 되는 결론: 보조 판정기가 입력을 낫게 한다, few-shot이 좋다/나쁘다, 조합의 +2.8점이 어느 한 설정의 것이다, 0.30점 차이의 관문 통과가 튼튼하다.
- 홀드아웃은 아직 열지 않았다(0/3회 사용).

### 출력 판정 시간 초과 분석 (저장된 실행 기록, 호출 0)

토큰 상한별로 출력 판정 호출의 실패를 모았다(출력 단독 실측 포함, 실행 9개).

| 토큰 상한 | 호출 | 잘림(`finish_reason=length`) | 시간 초과 |
|---|---|---|---|
| 800 | 448 | 26 (5.8%) | 1 (0.2%) |
| 1200 | 64 | 0 | 1 |
| 1600 | 640 | 0 | 6 (0.9%) |

1600의 6건: 출력 단독 2회차 2/128, 이번 3회 4/192. 조합 3회·확인 1회·출력 단독 1회차는 0/320.

- **새로 생긴 문제가 아니다.** 1600에서 시간 초과는 처음부터 약 1%였다(이 절은 `s29-r10`을 재기 전 집계다. 더한 값은 아래 "출력 판정 호출의 지연과 토큰" 절에 있다). 위에서 "앞선 실행에서는 0건"이라고 본 것은 출력 단독 실측의 2건을 빼고 센 것이다.
- **이번 3회가 유난히 나쁜지는 가를 수 없다.** 4/192 대 나머지 2/448은 한쪽 Fisher p = 0.07이다. 약 1%의 바탕 비율과 잡음으로도 설명된다.
- **긴 입력 탓이 아니다.** 시간 초과가 난 5행의 후보 답변은 35–113자(전체 중앙 55자, 최대 196자), 발화는 50–324자다. 한 행(`pub-ddbd0df5`)이 3회 중 2회 걸렸다.
- **800에서 잘리던 행과 겹친다(약한 근거).** 1600에서 시간 초과가 난 5행 중 3행이 800에서 잘린 적이 있는 행이다(잘린 적이 있는 행은 64행 중 약 14행이라 우연이면 1행쯤). 같은 행에서 nano가 길게 생각하는 경우가 있고, 상한 800에서는 잘림으로, 1600에서는 대부분 성공하고 일부가 12초를 넘는 것으로 읽힌다. 추정이다.
- **지금 기록으로는 더 못 본다.** `runs/`의 행 기록에 호출별 지연과 출력 토큰 수가 없다(`LLM` 결과에는 `latency_ms`·`completion_tokens`가 있다). 12초 근처에 몰려 있는지, 토큰을 얼마나 쓰다 끊겼는지를 알려면 하네스가 이 두 값을 행 기록에 남겨야 한다.
- 재시도는 이 실패를 구하지 못한다. 첫 시도가 12초를 쓰면 요청 예산 20초에서 8초가 남아, 같은 호출이 다시 12초를 넘기면 마감에 걸린다.

## 10회 실측 시도와 429 (같은 날, `s29-r10`)

호출별 지연·토큰 기록(`gr/s2.9-call-metrics` `cde642b`)을 넣고 default 설정을 10회 재려 했다. **4회차 도중부터 API가 HTTP 429를 돌려줘 유효한 것은 앞의 3회뿐이다.** 하네스 기록의 `rate_limit`은 상태 코드 429에 붙인 이름이다(`llm.py` `_status_code`). 응답 본문의 오류 종류는 이때 기록하지 않았다.

| 회차 | 가드 점수 | 입력 호출 | 출력 호출 |
|---|---|---|---|
| 1 | 84.84 | 311 성공 | 64 성공 |
| 2 | 82.76 | 311 성공 | 64 성공 |
| 3 | 83.51 | 311 성공 | 60 성공, 시간 초과 4 |
| 4 | 70.82 | 76 성공, 429 235 | 17 성공, 429 47 |
| 5–8 | 68.68 | 전부 429 | 전부 429 |
| 9–10 | 68.68 | 429 또는 하네스 호출 상한(5,000) | 같음 |

- **429의 사유는 이 실행에서 확인하지 못했다.** 이 실행에서 성공한 호출 약 1,220회(약 9분) 뒤부터 429였다. 오늘 누적 성공 호출은 약 12,600회 이하다. 실행이 끝나고 약 15분 뒤(UTC 14:31) 한 번 보낸 확인 요청도 429였고 `Retry-After` 헤더는 없었다. 상태 코드와 헤더만 봤고 본문은 읽지 않았다.
- **뒤에 확인된 응답은 크레딧 없음이다(2026-11-14 추가).** 11/14 0시에 튜터 담당이 확인한 응답은 HTTP 429 `insufficient_quota`("You have no credits remaining")였다. 채팅·임베딩 모두 같았고 새로 받은 키도 같았다(PR #144 리뷰). SPEC §3은 "API 키의 호출 한도는 따로 없습니다", §7.1은 "크레딧: 기본적으로 제한이 없고"라고 한다. 그래서 이 문서는 "속도 제한이 있다"고 적지 않는다. 11/13의 429가 같은 사유였는지는 기록이 없어 모른다. 운영진 확인 중이다.
- **막힌 뒤에도 하네스가 약 3,700회를 더 보냈다.** 429마다 한 번 재시도하고 다음 행으로 넘어가서, 실행당 상한 5,000회에 닿을 때까지 계속했다. 그때 하네스에는 "연속 429면 멈춤"이 없었다. 이 뒤로 호출을 멈췄다. PR #151이 연속 20회에서 멈추게 했다(종료 코드 6). 막힌 키에 약 3,700회를 더 보낸 것은 SPEC §7.1("어뷰징이 감지되면 1회 경고 후 API 키를 회수합니다")에 비춰 남겨 둔다. 경고를 받았는지는 확인하지 못했다.
- **유효한 6회(앞 절 3회 + 이번 3회)의 가드 점수는 82.76–85.71이다.**
- **nano가 전부 실패했을 때의 점수는 68.68이다**(kNN·LR 기본 범주, 출력은 규칙 ②와 기본값). block F1 0.636, 범주 정확도 0.448, 출력 평균 0.790. 키가 막히거나 API가 죽은 채 채점받으면 이 점수 근처가 된다.

### 출력 판정 호출의 지연과 토큰 (유효한 3회, 192호출)

| | p50 | p90 | p95 | p99 | 최대 |
|---|---|---|---|---|---|
| 지연(초) | 4.1 | 7.0 | 8.7 | 12.0 | 12.1 |
| 출력 토큰(성공한 호출) | 478 | 827 | 960 | 1,295 | 1,357 |

- 지연은 출력 토큰 수를 따라간다(상관 0.81, 토큰당 약 8.6ms).
- **`read` 한도 12초가 토큰 상한 1600보다 먼저 걸린다.** 1,600토큰이면 약 13.8초라 한도를 넘는다. 12초 안에 끝나는 것은 약 1,390토큰까지다. 시간 초과 4건은 모두 정확히 12.0–12.1초에 끊겼고 재시도 없이 끝났다(시도 1회). 성공한 호출 중 10–12초가 3건 있다.
- 즉 시간 초과는 "토큰을 1,400개 넘게 쓰는 호출"이다. 800에서는 잘림으로, 1600에서는 12초 시간 초과로 나타난다. 앞 절의 추정과 맞는다.
- 고치는 길은 둘이다: 출력 호출의 `read` 한도를 14–15초로 올리거나(요청 예산 20초 안), 토큰 상한을 약 1,300으로 내린다. 어느 쪽이 나은지는 재지 않았다.
- 4건이 모두 3회차(429가 시작되기 직전 회차)에 몰려 있다. 이유는 모른다.
- **합친 코드로 잰 유효 6회의 출력 판정 실패는 1·1·2·0·0·4/64, 합쳐서 8/384(2.1%)다. R14-D8의 2%를 넘는다.** 모두 시간 초과이고 잘림은 0이다. 1600 전체로는 10/832(1.2%)다(앞 절의 6/640에 이 3회의 4/192를 더함). 값(`read` 12초, 토큰 상한 1600)은 그대로 둔다. 다음 조치는 API가 다시 응답하면 위 두 안을 재서 고르는 것이다. ADR-0014 "S2.9 수정"에 같이 적었다.
- 입력 판정 호출(유효 933호출)은 p95 3.4초, 최대 8.3초, 출력 토큰 p99 519로 한도와 거리가 멀다.

## 3회 확정 실험의 몫 (R14-D7, 2026-11-14 추가)

R14-D7의 상한은 범위 비교(후보 3회 범위가 기준 범위와 겹치지 않음)로 채택을 정하는 확정 실험이 입력 1회·출력 1회·예비 1회다. 지금까지의 3회 실험을 이렇게 센다.

| 실험 | 결정 기준 | 몫 |
|---|---|---|
| 예시 없음 대 v1 (입력 단독, [input-screening-1](2026-11-13-input-screening-1.md)) | 범위 비교. 미채택(S2.9에서 재현 안 됨) | **입력 1회** |
| 토큰 상한 1600 대 800 (출력 단독, [output-v1-solo](2026-11-13-output-v1-solo.md)) | 실패율 관문(R14-D8). 점수 범위로 정하지 않았다 | 없음 |
| 조합 대 default (이 문서) | 범위 비교(`nano_span`). 예시 없음을 한 번 더 봤다(미채택) | **출력 1회** |
| 합친 코드 3회, `s29-r10` 3회 | 같은 설정을 다시 잰 것. 비교 없음 | 없음 |

- 남은 것은 예비 1회이고 #152 입력 v2 대 v1 확정에 쓴다. 그 뒤에는 범위 비교 확정 실험이 없다.
- 입력 쪽은 이미 두 번 봤다(예시 없음을 입력 단독과 조합에서). v2까지 범위 비교는 3번, 3회 실험은 5개다.
- v2 확정은 실측 전에 비교 지표와 "겹치면 v1 유지"를 적어 두고, v1을 지금 기본 설정(1600, `nano_span` 켬)으로 같은 묶음에서 다시 재 비교한다. 앞선 v1 범위와 비교하지 않는다.
- `nano_span`의 채택 근거는 가드 점수 범위(겹침)가 아니라 저장된 응답의 정밀도(0.96–1.00, ADR-0014 "S2.9 수정")와 출력 지표다. 범위 비교를 한 실험이라 몫은 센다.
- 이 셈은 council(4명 일치)로 정했다. 남은 이견: 같은 320행의 오류 분석으로 만든 v2를 같은 320행으로 확정하면 치우침이 5%보다 크다. 홀드아웃 열람 1회를 v2 대 v1에 쓸지는 정하지 않았다.
