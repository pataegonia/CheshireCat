# S2.10 혼합 부하 시험과 v1 제출: 가드 300 + 튜터 300 · 동시 64

작성 2026-11-15 · 담당 danielcho02 · 계획: C2 §S2.10, PRD GR-10·GR-09, SPEC §3·§9 · 이전 실측: [2026-11-13-load.md](2026-11-13-load.md)(가드 단독, 설정 6.0.2)

채점기와 같은 모양으로 가드·튜터 혼합 600요청을 한 프로세스에 보냈다(동시 64, 요청당 30초 제한). 그 뒤 같은 서버로 v1을 제출했다. 혼합 실행은 채점하지 않았다.

## 실행

| 항목 | 값 |
|---|---|
| 어디서 | 런박스(C-8, CPU 8개), 서버와 부하 도구가 같은 기계. `uvicorn app:app`(가드 + 튜터 한 프로세스, LLM 게이트 64 공유) |
| 코드 | main `f7d386a`(#180 부하 도구 + 튜터 #172·#164, 튜터 토글은 모두 기본값). 가드 설정 6.0.3(`1b4dc92350ff`, 영어 프롬프트). 튜터 `verify`·`guard_classify`·`evidence_check`·`inline_cite` off |
| 요청 | 홀드아웃 묶음을 뺀 가드 행 → 300, 튜터 행 → 300, 시드 13으로 섞음. 후보 답변이 있는 가드 요청 121개. 가드 5개는 이력을 약 1MB로 부풀림. probe(토큰 없는 POST `/guard`, 401) 40개 |
| 순서 | 짧은 실행(가드 10 + 튜터 10) → 서버 새로 띄움 → 본 실행 → KB 검색 측정 → 같은 서버로 v1 제출 |
| 도구 | `python -m guardrail.eval.load --tutor-url … --n 300 --tutor-n 300 --big 5 --probe --access-log …`(#180) |
| 호출 | 짧은 실행 20요청, 본 실행 600요청(가드 nano 약 421회 + 재시도, 튜터 주 호출 약 300회), 서버 기동 3회(기동 때 nano 파라미터 시험 호출), v1 제출 1회(채점기 600요청). 혼합 실행은 이번 작업에서 정한 상한 2회 중 1회 |

## 이 시험이 말하지 않는 것

- **원인 분리.** 11/13 가드 단독(p95 9.15초)보다 p95가 크게 낮다. 코드(영어 프롬프트 6.0.3)와 그날 API 상태가 함께 달라 어느 쪽 덕인지 가를 수 없다. 혼합 1회 값이라 새 기준선으로만 쓴다.
- **튜터 내부 실패.** 주 호출이 실패해 튜터가 대체 action을 낸 경우는 접근 로그 오류 칸에 남지 않아 이 도구로 보이지 않는다.
- **게이트 대기.** 서버 로그는 요청 전체 시간만 남긴다. probe는 루프 막힘만 본다.
- **429.** 실패가 0건이라 없었다고 보지만, 서버는 상태 코드를 따로 남기지 않는다.

## 결론과 다음

- 채점 모양의 혼합 부하에서 GR-10 수용 기준(시간 초과 0, 가드 p95 ≤8초, 전체 약 2분 이하)을 모두 넘었다. S2.10 완료.
- v1 제출 기록: 총점 83.73(튜터 77.75, 가드 89.71), 오류 0.
- 조정 PR은 내지 않는다(council D2). ADR-0014 S2.9 수정의 `read`·토큰 상한 후보는 출력 기본값이 다시 2%에 가까워질 때 본다.
