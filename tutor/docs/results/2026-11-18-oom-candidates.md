# 튜터 점수 후보 점검 (2026-11-18 낮~오후, yang-co1)

최신 동결 구성 위에서 튜터 점수를 더 올릴 후보를 점검했다. 그 가운데 하나(E 보내는 때를 T 뒤로, `oom_schedule`)를 이 PR에 넣는다.

**이 세션에서 확인한 것:**
- 실제 제출 점수가 오른다는 것은 확인하지 않았다.
- 개발 측정에서 `oom_gate: all`을 넘는다고 확인된 후보는 없다.

## 수치의 종류

- **개발 실측**: 공개 교차 검증 160행(홀드아웃 40 제외)을 운영진 gpt-5-nano로 실제 호출해 잰 값이다. 판정은 로컬 채점기(같은 nano)이고, 개발 PC에서 동시 8로 돌렸다.
- **팀 세트**: `tutor/eval/team_cases/tutor.jsonl` 45행이다. 공개 밖 문항이고 정답 사실 라벨은 없다.
- **호출 0회 계산**: 정규식·검색 순위만으로 계산한 값이다.
- 질문·답 본문은 남기지 않았다. 행 id·범주·숫자만 적는다. 홀드아웃 40행은 정규식·검색을 돌리기 전에 먼저 뺐고, 사용 0회다.
- PC 지연은 런박스·제출 지연과 다르다. 지연 관문 판단에는 쓰지 않는다.

## 4. E 이름 찾기 형태 보강(`named_term_forms`, 이 PR에 없음)

- 따옴표·괄호 안 명칭과 복합 머리말까지 찾아 E를 부르는 안이다.
- 공개 개발 160·팀 45에서 E 대상이 `named_term`과 완전히 같다(11 대 11, 0 대 0, 호출 0회 계산).
- 효과가 난 곳은 이전 세션이 만든 28문항뿐인데, AI 도구가 쓴 문항이라 TU-16상 팀 세트로 쓸 수 없다.
- E를 모든 요청에 부르는 `all`이 이 안의 대상을 모두 포함한다. 그래서 넣지 않는다.

## 5. `oom_gate: all`과 후보 A~D

팀원 실제 제출 5대5(가드 6.0.8 또는 6.0.10, 커밋 미상): 튜터 84.70 → 86.15(+1.45, 5쌍 모두 양), 가드 90.58 → 89.40(−1.18), 총점 +0.14였다.

**가드 하락은 아직 확정이 아니다.**
- 쌍별 가드 차이는 −0.72·−1.67·+0.68·−3.00·−1.19다. 쌍 안 부호 뒤집기 정확검정으로 p 0.125다.
- 같은 가드 코드도 제출마다 87.04~93.42로 흔들렸다(#235).

**`all` 경로 추적:** 개발 160 × 2, 판정 없이 단계별 결과만 메모리에서 기록했다(T 이름표·주 호출 action·E 입력 섹션·E found·최종 action).

| 값 | `named_term`(같은 코드) | `all` |
|---|---|---|
| action 정답(160 중) | 148 · 145 | 147 · 141 |
| E 호출 | 약 11 | 125 · 125 |
| E 호출 중 직렬 T가 주 호출 없이 끝낸 요청 | — | 6 · 4 |
| E가 answer → abstain으로 바꿈: 정답 abstain / 그 밖 | — | 6행 / 5행(정상 3·PII 1·주제 밖 1, 모두 2회 중 1회) |

공개 세트에서 `all`이 이득으로 보이지 않는 것은 예전 결과(−0.60)와 같다. 비공개 제출과 방향이 다르다.

| 후보 | 진단 | 판정 |
|---|---|---|
| A. E를 T 뒤로 | E를 덜 보낼 수 있는 요청이 3~4%다(T가 끝내는 요청). 효과는 작고, 판단 경로는 같다 | **이 PR. 6절** |
| B. E 프롬프트에 대상·속성 대조 | E만 따로 불러 같은 입력에서 비교했다(125행 × 3회 × 두 판, 호출 750). 순 기대 action −1.33행(자료 밖 고침 −0.17, 정상 오차단 +1.17), 튜터 대략 −0.64, 부트스트랩 [−6.5, +3.67]. 문항별로 양쪽으로 크게 뒤집혔고 E 시간 초과도 33 → 43으로 늘었다 | 기각 |
| C. E 근거에 대화 1위 보완 | E가 정상 질문을 잘못 막은 4행 모두 정답 섹션과 대화 1위가 이미 E 근거에 있었다 | 전제 거짓, 중단 |
| D. 근거 불일치 요청 선택적 재작성 | `all` + 직렬 T의 설정 검사 상한이 이미 4회다(주 호출 2(재시도) + T + E). writer를 더하면 5회 | 보류 |

D의 4회 상한은 대회 규정이 아니라 튜터 PRD TU-13의 팀 규칙이다. SPEC §3은 API 호출 한도가 없다고 하고, 과한 호출만 어뷰징으로 볼 수 있다고 한다(§7.1). 상한을 바꿀지는 지연(요청 예산 20초, 외부 30초)과 함께 팀이 정한다.

## 6. 이 PR: `toggles.oom_schedule`

| 값 | 동작 |
|---|---|
| `with_request` | 지금처럼 요청 시작 때 E를 보낸다 |
| `after_intent` | 직렬 T가 주 호출 없이 끝내는 요청(refuse·위기 고정 문장)과 주 호출 전에 끝나는 요청에는 E를 보내지 않는다. 주 호출 바로 앞에서 보내고, E 마감은 요청 시작부터 센다 |
| `after_intent_fresh` | 같은 순서에 E 마감만 E 시작부터 센다(요청 마감 안) |

- T 실패·약한 이름표·신호 없는 탈옥 이름표처럼 주 호출로 가는 요청은 E를 그대로 부른다.
- E는 최종 answer에만 쓴다. 흐름이 예외로 빠져도 띄운 E는 취소한다.
- 요청당 nano 호출 수는 늘지 않는다.
- 테스트: `tests/tutor/test_oom_schedule.py` 24개. 확인하는 것:
  - T가 끝내는 요청에서 E 0회
  - T 실패 시 E 유지
  - 마감 두 방식
  - 예외 시 취소
  - 호출 상한
  - 잘못된 값 거부

**같은 시간대 비교(개발 160, `oom_gate: all`, 판정 없음, 연달아 1회씩, 11/18 17시대):**

| 값 | `with_request` | `after_intent_fresh` |
|---|---|---|
| 튜터 nano 호출 | 407 | 404 |
| E 호출 / 그중 주 호출 없이 끝난 요청 | 125 / 10 | 121 / 0 |
| E가 답을 낸 요청 | 94 | 94 |
| action 정답(160 중) | 147 | 141 |
| E가 answer → abstain: 정답 abstain / 그 밖 | 5 / 0 | 5 / 4 |
| 시간 초과 T / 주 호출 / E | 6 / 5 / 27 | 1 / 1 / 15 |

- 설계대로 E를 덜 보낸다. 다만 아끼는 양은 개발 기준 1% 안팎이다.
- action 정답 차이(−6)는 E가 같은 횟수로 답한 가운데 E 판정이 갈린 몫이다(같은 `with_request`도 앞선 추적 두 회에서 action 정답 147·141, 잘못 바꾼 수 2·3). 1회씩이라 흔들림과 가르지 못한다. 이득도 손해도 확인하지 않았다.
- 시간 초과 수는 API 상태가 시간대마다 달라 설정 효과로 읽지 않는다.
- 이 비교 전에 돌린 같은 측정 1회는 개발 PC에서 테스트를 함께 돌리던 중이라 T 시간 초과 9~10, p95 20초로 무효 처리했다(T는 E보다 먼저 돌아 이 변경과 무관).

**동결 설정에서 `after_intent_fresh`를 켠다(담당자 결정, 11/18).**
- E 부하가 조금이라도 줄면 켠다는 기준으로 정했다.
- 점수 효과는 확인하지 않았다. `with_request`로 되돌리려면 설정 한 줄이면 된다.
- 지금 동결 설정의 `oom_gate`는 `named_term`이라, 이 값의 효과는 E 대상 요청(약 7%)에만 걸린다. `all`과 함께 쓸 때 위 표의 차이가 난다.

## 7. 재현

- 측정 스크립트(저장소 밖, 서버가 읽지 않음): 경로 추적, 같은 답 재판정, E 단독 비교. 본문은 메모리에만 두고 파일에는 id·enum·숫자만 남겼다.
- 운영진 API 호출: 이 문서의 실행 합계 약 9,700회. 무효 실행 3건이 포함된다(API 장애 2, 동시 테스트 부하 1).
