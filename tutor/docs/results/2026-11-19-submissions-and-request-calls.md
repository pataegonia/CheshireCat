### 요청 하나의 흐름(`tutor/judge/flow.py`)

1. **대화 정리와 결정적 신호.** 빈 발화나 자모·기호뿐인 발화는 LLM 없이 고정 clarify로 답한다.
2. **T 시작(직렬).** 8초 안에 오면 이름표로 정한다.
   - refuse·위기 고정 문장이면 주 호출 없이 끝낸다.
   - redirect·scaffold 고정 문장은 주 호출을 불러 본 뒤 정한다.
   - 8초 안에 안 오면 주 호출을 먼저 보내고 T는 나중에 받는다.
3. **E 시작.** 판단 대상에 KB에 없는 이름 붙은 말이 있거나 영어 발화일 때만 부른다. 시작 시각부터 9초를 세며 주 호출과 병렬로 돈다.
4. **검색과 주 호출.** 상위 5개 섹션을 근거로 주 호출을 보낸다.
   - 12초 안에 안 끝나면 같은 요청을 한 번 더 겹쳐 보내고 먼저 성공한 쪽을 쓴다.
   - 실패하면 자료 인용 답이나 고정 문장을 낸다.
5. **덮기와 인용.** 대행 보정 → T 덮기 → 규칙 A(튜터 발화까지 넣은 질의로 1위를 다시 찾음) 인용 더하기 → 후처리.
6. **마무리.** 최종 answer인데 E가 "근거에 없음"이면 자료 밖 고정 문장(abstain)으로 바꾼다. 아니면 인용 1위 섹션의 자료 문장을 덧붙인다.

## 4. 이번 PR의 코드 변경

기본값에서는 응답이 제출 판과 같다. 상한 8회는 최악 5회보다 크고, 나눠 쓰기는 꺼져 있다.

### 4-1. 요청당 nano 시도 상한(`llm.request_max_calls`, 관리 상한 8)

- 11/19 사용자가 요청당 4회를 넘기는 것을 허락했다. 4회는 대회 규정이 아니라 팀 설계 기준(TU-13)이었다. 대회 규정은 요청당 30초·동시 64이고, 과도한 호출은 금지다. 8은 후보 실험의 관리 상한이며 대회 규정이 아니다.
- **최악 시도 수 계산**: `tutor.runtime.config.request_calls(cfg)`가 (정상, 최악)을 돌려준다.
  - 최악 = 주 호출 1 + 재시도(T와 classify를 함께 켜면 0) + 겹쳐 보낸 주 호출(`main_hedge` < `main`) + T + classify 2 + `judge_output` + E.
  - 예전 검증(`Toggles._not_built`)은 겹쳐 보낸 주 호출을 세지 않았고 4를 코드에 박아 두었다. 이제 최악이 `request_max_calls`를 넘으면 로드에서 거부한다.
- **보내기 직전 예약**: `tutor.runtime.llm.RequestQuota`.
  - `pipeline.respond`가 요청마다 하나 만들어 ContextVar에 건다. 그 요청의 T·E·주 호출·겹쳐 보내기 작업이 같은 객체를 본다.
  - 게이트를 잡은 뒤 확인과 예약을 await 없이 이어서 하므로, 병렬 작업이 동시에 상한을 넘지 못한다.
  - 막힌 시도는 `capped`로 따로 센다. `run_local`은 이 수를 결과 JSON `tutor_llm.capped`에 남기고, 0이 아니면 그 실행을 무효로 본다.
  - 가드 LLM(classify·judge_output)과 임베딩은 이 예약에서 세지 않고, 설정 검증만 센다.
- **측정 도구**:
  - `run_local` 예상 호출: v2는 3회와 설정의 정상 경로 수 중 큰 쪽, 베이스라인은 1회.
  - 화면에 정상·최악·상한을 함께 낸다.
  - #83 관문 요약(`tutor/eval/gate.py`)의 요청당 nano 기준은 설정 상한을 쓴다.

### 4-2. 한 요청 안 질의 임베딩 나눠 쓰기(`toggles.share_query_embedding`, 기본 끔)

- 영어 장치를 켜면 영어 요청 하나가 질의 임베딩을 최대 3번 부른다(E 근거 묶음·주 호출 근거·규칙 A). E와 주 호출은 같은 질의 문자열이다(#243 기록: 3회 측정에서 예상 48회, 실제 106회).
- **동작**: `EmbeddingSearch.for_request()`가 요청용 사본을 만들고, `RequestEmbeddings`가 같은 질의 문자열이면 진행 중이거나 성공한 호출 하나를 함께 기다린다.
  - 요청 사이에는 나누지 않는다. 요청이 끝나면 남은 호출을 취소하고 버린다(TU-18).
  - 실패한 결과는 지우고 다시 쓰지 않는다. 뒤에 오는 쪽은 새로 부른다.
  - 한쪽이 시간 초과로 빠져도 다른 쪽 호출은 이어 간다. 아무도 기다리지 않게 되면 호출을 취소한다. 나눠 쓰지 않을 때 시간 초과가 호출을 접던 것과 같다.
- 순위는 나눠 쓰지 않을 때와 같다(테스트로 확인). 품질 후보가 아니라 호출·지연 여유를 만드는 기반이다. 켜기 전에 런박스에서 영어 문항으로 켬·끔 응답이 같은지와 임베딩 호출 수를 확인한다.

## 5. 해 보고 멈춘 후보(11/19 설계 인계 순서)

### 5-1. R: 질문별 근거 섹션 고르기(1단계에서 중단)

- **가설**: #235 8행 진단(정답을 아는 oracle)에서 정답 섹션 하나만 주면 사실/충실이 0.500/0.917 → 0.708/1.000이었다. nano 선택기 1회가 질문마다 섹션 1~2개를 고르면 그 이득 일부를 얻는다.
- **선택기**: 출력은 번호 enum `first` 1~5, `second` 0~5, `broad_context`다. 묶음 밖 번호는 기존 상위 5개로 돌린다. 프롬프트 예시는 지어낸 자료다.
- **1단계 탐침**: 기준선과 같은 BM25 상위 5개 묶음을 썼다. 공개 교차 검증 근거 있는 한국어 93행 + 팀 근거 있는 27행 = 120행 × 3회, 운영진 API 361회.
  - 영어 전용 행은 뺐다. 개발 PC에 임베딩 환경변수가 없어 기준선 영어 묶음(임베딩 순위만)을 재현할 수 없었다.
- **실행 전에 정한 기준과 결과**(근거가 묶음에 있는 348건):

| 기준 | 결과 | 판정 |
|---|---|---|
| 좁힘 ≥ 50% | 99.7% | 통과 |
| 좁힌 것 중 근거 버림 ≤ 8% | **21.9%** | 미달 |
| 근거 지킴 R > 상위 2개 자르기 | R **78.2%**, 상위 1개 83.6%, 상위 2개 94.8% | 미달 |
| 지연 p95(PC) ≤ 6초 | 5.99초 | 경계 |

- **원인**: 정답이 검색 1위인 291건 중 45건에서 R이 1위를 버렸다. 정답이 1위가 아닌 47건 중 R이 정답을 고른 것은 22건뿐이다(순 −23건).
  - `broad_context`는 348번 중 1번뿐이었고 평균 고른 수는 1.02였다. "모르면 넓게"가 작동하지 않았다.
  - 근거 2개가 필요한 팀 문항(9건)은 6건에서 하나를 버렸다.
- **결론**: 생성 실험(2단계) 전에 멈췄다. 같은 세트로 프롬프트를 고쳐 다시 재지 않았다. 실패한 것은 미리 정한 프롬프트·스키마 하나를 섹션 하나짜리 정답 라벨에 견준 결과이고, "질문별 선택"이 불가능하다는 뜻은 아니다.
- 선택기 코드는 참고용 브랜치 `tutor/exp-r-section-select`에만 두고, 이 PR에서는 뺐다. 켜도 작동하지 않는 토글을 남기지 않기 위해서다.

### 5-2. E3: 같은 E를 한 요청에서 세 번 묻고 다수결(API 0으로 확인, 구현 안 함)
